# Testing Petrina

Development guidance for coding agents. Product contracts live in [design.md](design.md) and [ux.md](ux.md); contribution rules live in [AGENTS.md](../AGENTS.md#checks-and-test-cost).

The [test-layer design](testing/layers.md) defines behavior ownership, subsystem directories and the migration audit. New tests belong under `test/<layer>/<area>/`; existing mixed files are being reviewed and split. A moved file is not proof that its fixture or assertions have been audited.

## Required checks

Use the Bun version pinned in CI, Git and Node.js. From the repository root, install the locked dependencies and the browser they require before running checks:

```sh
bun install --frozen-lockfile
bun run test:install-browser
```

On Linux use `bun run test:install-browser --with-deps` to provision the browser's system libraries too. Installation is setup, never part of an individual test. Then run:

```sh
bun run typecheck
bun run test
```

Required tests use scripted coding tools, GitHub and account reports. They do not require a developer's login, installed coding harness, saved Git identity or personal configuration.

Core, orchestrator and desktop use Vitest; engine, agent-runtime, repositories, storage, platform and shared test-support tests use Bun. Keep the required engine suite fully parallel. A genuinely required extra full-suite validation (such as explicit Linux acceptance) must use [the shared validation queue](coordination.md#required-extra-full-validation), never a competing full suite or polling other processes. It runs only Petrina's last saved commit and tree, excluding working edits: hand new work back for Petrina to save, then request that version. Agents never commit or publish it themselves. Without Petrina's command tools, ask the coordinator. Focused tests, focused container regressions and preparing a local image remain allowed under existing fixture, cleanup and tool-permission rules. An isolated timing failure passing alone does not rule out a race.

`bun run test` takes no arguments. File selectors and options fail before repository scanning, reports or suite launches; `--help` or `-h` alone prints usage without running tests or writing a report. For a focused run, use a workspace command below; focused results never replace this required full check.

The focused Bun wrapper verifies explicit file and directory paths before starting tests, including paths resolved through `--cwd`. A missing path fails the whole invocation even when another selector matches; Bun otherwise silently ignores that typo. Bare name filters remain Bun's responsibility. Use `--option=value` for advanced runtime options to keep their values unambiguous.

The full check first enforces test conventions and the canonical native package commands, exiting before writing reports if either is invalid. Core, desktop and orchestrator then run independently in order, including after another preliminary failure. Only after all three pass does one Bun execution run all native workspaces in a shared normal worker pool. A native package failure does not prevent its peers from reporting. Shared execution may not silently bypass custom package setup: declare preparation and teardown explicitly rather than adding hidden lifecycle scripts or package-specific Bun configuration.

Before those suites, the runner checks that the locked browser dependency resolves to an accessible executable in the same private environment. Missing setup stops the run before suite execution; tests never install a browser. This file/access check does not prove that the browser can launch or that its system libraries are installed. Test inputs must still match the validated snapshot after prerequisite preparation and after affected-test observation; a concurrent edit cannot introduce unvalidated commands into the run.

Before execution the runner records every expected test file. Each workspace needs complete structured outcomes, consistent case counts and its exact file manifest. Truncated reports, unfinished cases, missing packages and entirely skipped execution cannot establish a pass. Explicit platform/integration skips are counted separately. Workers, assertions and test deadlines stay unchanged, with no retries. Every workspace must pass in that invocation, with its source fingerprint and Git revision unchanged at the end; separate runs never combine into one pass. A stop requests bounded settlement of the active execution; later executions do not start and no closing summary is printed.

Each run saves `impact.json`, the expected `files.json` manifest and `results.json` in a unique ignored `.test-results/` folder. Results record the starting commit/tree, input fingerprint, clean-checkout observation, OS/architecture and Bun version. Moving HEAD invalidates the run even when source bytes stay identical. `executions` records each actual exit and duration once; per-workspace `results` records case counts, failed files and selection misses with an `executionId` reference. A passing peer retains its own passing case counts when another package fails the shared native execution. Unstarted work has a reason and no invented duration or selection accuracy. `scope` is complete only after every workspace supplies complete evidence and every execution reports its outcome without interruption. CI retains the structured reports and timing artifacts for its platform.

Petrina runs this as one Tests check. A failed quick phase is an ordinary failed check, returned to the Builder under the same rules, failure reuse and two-return allowance; only a later complete pass ends the failure episode. Petrina's forced stop ends the runner without a final report, and its own stopped-check record is the evidence. Each CI platform runs the same command independently, so an engine failure specific to one platform appears once that platform's preliminary suites pass.

UI changes also need light and dark and all three demos: `?demo`, `?demo=portfolio`, `?demo=first-run`.

The workspace registry in `packages/engine/test/quality/workspaces.ts` supplies package aliases, required suite paths, runner types and required execution membership. Add new test workspaces there; a new package must not disappear from the complete check. Production core/orchestrator dependency boundaries and lower test-layer resource restrictions are enforced before suites launch.

## Affected feedback

For early feedback on this repository, run `bun run test:affected --base <revision>` (default: `origin/main`, or `PETRINA_TEST_BASE`). Unlike `test:impact`, this command executes the selected files. It follows current test-file dependencies and exact-input coverage observations; changed fixtures, runner/configuration/dependency inputs, unknown mappings and stale coverage conservatively select the full set. A missing base also selects everything and records why.

Only selected workspace owners run, in their existing order, with one normal native worker pool. Native feedback selects exact files. Vitest feedback runs the whole selected workspace, preserving its normal script/configuration and avoiding its substring filename filters; these short suites provide bounded early feedback. Reports distinguish requested files from the expanded manifest. A selected preliminary failure holds native work. Expected files and structured case outcomes must be complete; skipped-only work, unknown exits, changed source and interruption cannot establish passing feedback. An empty selection explicitly records that no validation was performed.

Reports live separately under `.test-results/feedback/`, with `kind: affected-feedback` and `deliveryEligible: false`, even when selection included every file. They do not update full-suite timing hints or replace required-suite evidence. Full and affected executions share the same bounded native runner, private environment and report verification. The required `bun run test` command still runs every workspace and binds its evidence to the current integrated source.

This selector belongs to Petrina's Bun/Vitest repository. The generic engine does not infer test dependencies for other products; each product retains its configured full checks. Agents may use affected feedback before handing work back, and must keep actual check failures visible rather than repeating the command until green.

## Shared-host load diagnostics

For repeatable resource diagnostics, see [measuring test cost](testing/resources.md). `bun run test:resources` observes the unchanged full selection and normal workers; its reports cannot authorize delivery.

Ordinary focused tests and diagnostics, Petrina's required checks and the normal parallel full run need no extra permission. Deliberate host stress does: CPU busy loops, memory or disk fillers, process floods or many concurrent copies of a test can disrupt every task on the computer, even when investigating one focused test and bounded in time. The default test run must never deliberately saturate the host. A test needing real contention uses an isolated environment with hard CPU, memory and process limits (and relevant disk/I/O limits), or an explicit opt-in like the native browser tests' `PETRINA_BROWSER_CHECK`; opting in does not authorize host stress.

Prefer controlled release signals, fault injection or that hard-limited isolation when they prove the same behavior. Keep real native deadline and process-cleanup coverage where it is needed; fake-only success cannot replace it. If only real load on this computer can prove the behavior, ask through the existing `needsInput` Inbox question and wait for the coordinator to arrange a suitable window. State what resources will be loaded, the load and process caps, duration, cleanup, what else could slow down and what the safer approaches cannot prove. Never poll other tasks' processes to claim spare capacity or treat a quiet process list or low load as permission.

Every diagnostic helper must have its own deadline and a fixed process cap, remain owned by the invoking command, and stop if that command or the agent's turn is interrupted. Arrange parent-liveness watching or interrupt cleanup as well as the helper's own deadline: some command tools leave children running after timeout. Also apply the command tool's execution deadline, following [focused command limits](#engine-test-time-limits). Confirm all owned helpers stopped after success, failure, timeout or interruption, before trying changed work; report any cleanup that could not be confirmed. Never stop processes you did not start.

A diagnostic run, passing repeat or host-load reading stays diagnostic evidence: it never turns a failed mandatory check into a pass and does not by itself prove what caused a failure. Keep required-suite workers, test cases and production deadlines; do not retry until green. These are agent instructions, with no host reservation or automatic stress detection or cleanup. Coordinator handling of requests is in [the coordinator guide](coordinator.md#requests-to-load-the-shared-computer).

## Keep checks fast without losing coverage

Every full run adds to task and review-loop duration. Use direct core tests for decisions and focused engine fixtures for effects. Run a complete workflow when its interactions are what the test proves; do not send every reviewer regression through unrelated design or check discovery.

Use explicit progress/release signals instead of sleeps and controlled clocks for time-independent decisions. Actual startup deadlines and stopping stubborn child processes need real wall-clock coverage. Measure costly new integration cases and the fully parallel run after fixture changes; report the results with the change. Do not trade away assertions, isolation or workers, or add retries and skips to obtain a faster result.

The full runner records Bun per-file wall times in `native-timings.json`, alongside the shared `native.xml` case report. File paths are relative to the shared execution folder (`packages/engine`), including companion packages. It reuses valid durations from the last complete stable successful run as ordering hints, so Bun starts measured slow files first at its normal worker count. Missing or invalid hints do not omit tests. The exact seed and its digest are retained with the run; `.test-results/timings/native.json` is an optional atomic cache, never passing evidence. Failed, interrupted or source-changing runs cannot replace it. JUnit adds concurrent cases' durations, so that sum is not a file's wall time. Look for idle-worker tails as well as slow cases. Divide large independent test groups into focused files with a shared owned fixture; keep cases that mutate shared module functions sequential within their file. For example, `test/extra-validation*.test.ts` shares `test/extra-fixtures.ts`, while each file owns its engines and writable folders. Never duplicate fixture policy or share those resources to make a split faster.

The shared Bun runner owns workers' temporary files and private Git helpers, reclaiming them after success, failure or interruption; Bun's isolated workers bypass exit hooks. Required and focused CLI executions use the same bounded process owner, inheriting output directly instead of retaining another log in memory. Each execution has a twenty-minute outer deadline, preserving individual test deadlines and normal workers. An interrupt allows five seconds for graceful settlement where the native owner supports it, then requests bounded owned cleanup; unavailable cleanup remains explicit. A native exit record prevents signalling a released handle, but a missing exit notification still makes the result incomplete.

`packages/test-support/src/environment.ts` is the canonical runner environment: a private home, application settings and Git configuration with a test identity. It admits OS/runtime essentials and explicit test controls, excluding inherited accounts, repository overrides and coding-tool configuration. The only provisioned content linked into the private home is Playwright's browser binary cache; it contains no personal browser profile. Native workers and the preliminary Bun command disable automatic dotenv loading, so a working folder cannot reload account variables after filtering. Scripted child programs own their runtime options too. Nested and simultaneous runs have separate homes and settings. Repository-local Git settings and identities explicitly supplied inside a test still work.

On macOS the runner puts each run under `~/.petrina/test-tmp` when the temporary parent is the normal session folder or system fallback, including their canonical paths and aliases. A custom temporary parent, including one inherited from an enclosing run, stays in place; only the run's own folder is removed. Real agents' browser files stay separately under `~/.petrina/b` for short socket paths and browser-owned recovery and cleanup. Engine tests' private browser folders go in a short folder the runner also owns in the system's temporary folder, reclaimed the same way. Repository helpers copy immutable prepared seeds into independent object stores, refs and configuration. Never share mutable repositories, alternates or engine instances between tests.

## Dependency boundaries

| Boundary | Test it with |
| --- | --- |
| Providers, GitHub and account reports | Scripted sessions for workflows, native fake agents for ACP and process contracts, local protocol services; explicit native integration opt-in for real accounts. |
| Git | Real Git, private repositories/configuration and local remotes. |
| SQLite | Private databases; real files for persistence, restart and durability cases. |
| Process lifecycle | Owned real programs for signals, crashes and cleanup; unavailable inspection is not proof of termination. |
| Workflow decisions and time | Small core tests and controlled events/clocks; real waits when the actual deadline is the assertion. |
| UI and browser | Component tests and selected real-browser workflows with provisioned binaries and private contexts. |

Keep the real transport, storage or process boundary when that interaction is the point of the test. Do not replace it with a mock that merely agrees with the implementation.

Generated child scripts resolve shared modules through their public package exports with `import.meta.resolve`, then embed that absolute URL; never reconstruct another package's source path. When a fixture waits for a program's marker, pass the owning operation to `waitForFile(path, { during: operation })` when available. A completed or failed operation with no marker ends that wait immediately and retains its failure. This does not shorten production timeouts or treat silence as progress.

Shared fixtures use portable APIs. Keep operations requiring native behavior behind an explicit fixture interface, with real contract tests for each supported implementation. `@petrina/test-support/fixture-files` owns directory aliases (Windows junctions and POSIX directory links), file links and native path spelling; `@petrina/test-support/commands` owns bounded test commands and their platform-specific cleanup. Reuse these boundaries instead of repeating OS switches in workflow setup. A native behavior test may assert its platform's contract; a workflow test should use the shared operation. Unavailable inspection is not a successful cleanup, and substituting an ordinary file for a symlink does not test symlink behavior.

Git hook and credential-helper contracts use `@petrina/test-support/git-program` for a real marker program and Git's own shell boundary. Keep shell quoting there, and retain positive controls proving the program and hook run before relying on their absence in a refusal test. Ordinary product checks still use argument arrays without a shell.

Production and fixture commands share `@petrina/platform/process-host` for process-group capability, owned spawn flags and bounded Windows tree termination. Adapter tests inject a private native executor and deadline, alongside a real owned-process control on Windows. The adapter performs the native operation; each caller must still establish which processes it owns and confirm its cleanup.

Use `test/file-faults.ts` to simulate refused picture copies or owned storage/worktree removal through an engine's private `files` interface. Preserve that fixture's interface across its restarts. Do not change process-wide filesystem functions or rely on permission bits to manufacture a workflow failure: permission semantics differ on Windows and under elevated users. Successful operations still use real files and Git registrations; the filesystem boundary retains real copy, missing-source and directory-alias removal controls.

Process-local effects stay out of child-process JSON configuration. Use `writeFixtureEngineOptions` from `test/engine.ts` when publishing an engine fixture's settings; it refuses file, session and probe adapters before writing. A child reconstructs its runtime effects through its fixture entry point. In-process restarts can keep their fixture's same private adapter.

Use `test/scripted-probes.ts` when a journey needs known installation/login observations but is testing another behavior. Declare each tool's actual fixture result, including unavailable and inconclusive answers; unspecified tools fail instead of consulting the machine. The real host still records and persists those observations. Readiness orchestration belongs to the portable controller's controlled-clock tests; native setup, process cleanup and login contracts keep actual probe processes. Do not replace those contracts with global Ready defaults.

`EngineProcess` uses that same command runner for app-mode fixtures: bounded startup, both output pipes drained, and owned cleanup on startup or exit-wait failure. Its `errors()` method reads collected stderr; do not read its process's already-owned output streams separately. Forced kills remain forced interruptions so the restart controls still exercise production recovery. Once a fixture creates an owner, protect setup before returning it with `setupWithCleanup` from `@petrina/test-support/setup-with-cleanup`; supply the actual bound shutdown/quit operation. Cleanup must reject if it cannot confirm completion. The helper awaits it on setup failure and preserves both failures; successful setup transfers cleanup responsibility to the caller's `finally`.

The Rust desktop host's lifecycle fixtures live in `apps/desktop/src-tauri/src/test_process.rs`. They start the test executable through `std::process`, announce readiness explicitly and use a private loopback control to observe and stop a handed-off child. Keep those tests portable: no `sh`, `sleep` or PID-based `kill` commands. Control closure detects a child left running after its desktop owner exited; the production lifecycle still uses the real owned child handle. Startup, inherited output pipes and retained-owner recovery exercise `engine_process` directly with those real actors. Stop-policy failure combinations use typed observations and a controlled clock; native deadline and termination checks remain separate. Run the full crate with `cargo test --locked --lib` from `apps/desktop/src-tauri`; a standard-library-only harness does not qualify the Tauri composition.

## Choose a focused test

From the repository root, choose the workspace explicitly. Do not append files or filtering options to the root `bun run test` command:

```sh
bun run --cwd packages/engine test test/name.test.ts
bun run --cwd packages/core test test/name.test.ts -t 'test name'
bun run --cwd apps/desktop test test/name.test.tsx -t 'test name'
```

Use an absolute working-copy path when starting elsewhere, for example `bun run --cwd /absolute/working-copy/packages/engine test test/name.test.ts`. If you change directories in a shell, join the commands with `&&` so a failed change stops the test command: `cd /absolute/working-copy/packages/engine && bun run test test/name.test.ts`. Do not put the test command on an unconditional next line or after `;`, where it could run from the wrong directory.

Core stops at the first failure; filter by name to investigate later cases. Core modules have no runtime dependencies: diagnostic scripts can import their source by absolute path without the whole suite. Keep those scripts, their working directory and `TMPDIR` in an uncrowded home folder on this Mac; moving just one leaves Bun's startup delay. Use the command tool's deadline; this Mac has no `timeout` program.

## Engine test time limits

Run engine tests through the runner, as above: `packages/test-support/src/run.ts` owns their fallback limit. It passes Bun `--timeout=720000` (twelve minutes) before your options, because Bun fixes a test's limit when it starts while fixture waits stretch up to eight times as the machine gets busier. Bun uses the last `--timeout`, written `--timeout 30000` or `--timeout=30000`, so a limit you pass replaces the fallback. A test's own limit, `it(name, fn, ms)`, beats both, shorter or longer. Bun ignores a `timeout` in `bunfig.toml`. Direct `bun test` without the runner, a `--timeout` or a test's own limit stops each test after Bun's five-second default, whatever helpers it imports; pass `--timeout` when a direct run needs longer.

Shared helpers never set limits: a `setDefaultTimeout` in an imported helper replaces an explicit `--timeout`, and in one Bun process only for the first file that loads it, so the limit would depend on imports and file order.

For a bounded focused diagnostic, give each test an explicit short limit and also bound the whole command outside Bun:

```sh
bun run --cwd packages/engine test test/name.test.ts -t 'test name' --timeout=30000
```

Run it under the command tool's execution deadline, normally two minutes. Bun's limit stops only a running test: it does not cover slow startup, a stuck or CPU-starved process, or a test with its own longer limit. A test that Bun reports as "timed out after 30000ms" is that test's result; a command stopped by the outer deadline is an incomplete check. Confirm the processes it started have stopped before trying again.

## Affected-test observation

`bun run test:impact [base-ref]` reports candidates from the current import/export graph, including changed tests and transitive dependents. The default base is the locally available `origin/main`; no network fetch or test execution occurs. Full runs use `PETRINA_TEST_BASE` when supplied. The report records the resolved base, HEAD and a content fingerprint of current inputs, including uncommitted files. Deleted or unmapped files, shared fixtures, configuration, dependencies, runner changes and unknown mappings conservatively select the full suite. Unresolved or computed imports include all their known test consumers. Invalid or unavailable Git information in the full runner falls back to the full suite.

This graph is not complete runtime coverage: subprocess entrypoints, file reads, generated programs, native code and external services can create additional relationships. No passing observation authorizes skips. Keep workflow integration tests for those interactions and use direct module tests for isolated decisions; lightweight engine helpers live in `test/fixtures.ts`, so they do not implicitly import the complete Engine.

Optional engine-file coverage can supplement the graph:

```sh
bun run test:coverage packages/engine/test/rules/testing/rejections.test.ts
```

This runs one exact test file through the isolated parallel engine runner and records executed-file LCOV edges after a pass on unchanged inputs. Collect files serially; each report belongs to its source, Bun version, platform and explicit browser-integration setting. Coverage only adds candidates. Missing coverage is labelled absent; stale coverage triggers a full selection. Coverage from spawned processes is not inferred, and a file-level map does not prove that every branch or scenario was exercised. Core and desktop retain Vitest's normal focused commands; no coverage package or selection mode is injected into them.

Dependency and coverage reports remain diagnostic; the explicit affected-feedback command above can execute their conservative selection. Subset evidence never authorizes delivery. The final delivery gate always requires every configured full check and hook on the current integrated tree and check definition. Reusing a pass requires unchanged inputs; a changed main tree or changed commands/hooks require verification again. Local landings serialize per product and reprepare if the destination moved. This repository's regression includes two changes that pass separately but fail together: the second cannot land on its old evidence. Petrina does not merge pull requests.

## Engine fixtures

- `test/support.ts` supplies `makeWorld`, local GitHub stand-ins through `EngineOptions.gh` and `remote`, scripted engines, and wait helpers. Configure agents with `Fakes.scenario`.
- Use `test/fixtures.ts` for private repositories, waits, temporary folders and fake-agent records without the Engine. Import `test/support.ts` when a complete workflow fixture or engine process is needed. Keep new tests named `*.test.ts` or `*.test.tsx` in their workspace's test folder.
- Run every program a test, fixture or stand-in starts with `runCommand`, and Git with `git`, `gitWith` or `runGit` (`@petrina/test-support/commands`, also exported by the fixtures). Each runs asynchronously under the worker's own deadline (Git's 30 seconds, stretched by `SLOW`, unless the caller gives one), succeeds only once its exit is reported with complete output, and on failure stops what it started within a short bound. While the runtime has not collected the program, cleanup pauses its process group before looking, and counts as confirmed only when everything it then finds stayed in that group, showed paused and has ended with the program's output. Beyond that group, only what the latest process list shows as the command's is signalled by number. Synchronous child calls (`Bun.spawnSync`, `execFileSync`, `spawnSync`, `execSync`) hold the whole worker until the exit is reported, so no deadline in it can run. Await commands and repository helpers (`makeProduct`, `makeWorld`, `repositorySeed`, `remoteRef`) before using their results, including in setup hooks and generated test programs.
- Only Git's own "not there" answer (`commitAt` or `remoteRef` returning undefined) means a ref is absent; any other failure fails the test, in the stand-in GitHub too.
- Tests in one native file must not combine concurrent cases with writes to the worker's `process.env`. Pass an explicit environment to the boundary, or put the environment-sensitive operation in an owned child. A serial native environment contract restores every changed key in `finally`, deleting originally absent keys. The convention check detects direct assignments, deletions, updates and standard environment-object mutators beside `.concurrent`, including renamed test functions and namespace imports. Aliases created in test code and arbitrary helper side effects fall outside this syntax check.
- Keep `engine.subscribe` callbacks synchronous: read a working copy's HEAD at that moment with `headNow` (Git's files, no program), or hold the workflow while running Git. `until` and `finish` wait for an asynchronous condition or answer before looking again; after waiting, an answer decides from `engine.getState()`.
- A generated check program may still call Git synchronously: the engine's check runner bounds it and stops its whole process group.
- Import fixture `Engine` from `test/engine.ts`. App-mode tests use the same module's `fixtureEngineOptions(dataDir, options)` with `launch`; never duplicate its defaults. It disables every provider's live account reader, native agent fallback, personal clone discovery and real terminals by default. GitHub/container operations need explicit stand-ins. Usage tests supply their own `usageCommands`. A missing or empty fake-agent command fails locally rather than launching the installed provider. Startup availability comes from fixture configuration, not the developer's installed tools. Boundary tests may inject their own `which`, `toolPath` and services.
- Import `EngineClient` from `test/client.ts` and the `CLI` entrypoint from `test/fixtures.ts`. They exercise the production parser, client and launcher with that same fixture policy, including detached starts, restart and MCP. Calling the production CLI directly can start live usage readers even when a test never queues a task. The convention check rejects runtime imports that bypass the fixture client. New test-only environment controls use the `PETRINA_TEST_` prefix so nested runners can preserve them without admitting production account or launch settings.
- A failed check looks for recorded machine sleep. Fixture `Engine`, the harness and `runChecks` from `test/fixtures.ts` supply no sleep records, so synthetic failures never read this Mac's power log. Interruption tests give each engine or run its own records through `EngineOptions.machineRecords` or `runChecks`'s last argument: `powerLogSleep` lines, `heldMachineRecords` for delayed, cancellable reads, or a failing source for unavailable records. Do not mock the shared reader. Test the native reader's command with a fake executor; a test that truly needs the live log passes `livePowerRecords` explicitly.
- Seed completed command scenarios with explicit execution facts from `@petrina/test-support/check-execution-facts`; a reported `ok` flag alone is not proof of completion. Keep missing historical facts and pending, running, stopped or uncertain-cleanup scenarios as such. Tests of actual execution use the native runner's observations instead of adding successful facts afterward.
- `ScriptedAgents` (`test/scripted-agents.ts`) supplies responses through the engine's session interface without spawning a process per turn. Pass its `start` as `startAgentSession` to the isolated Engine fixture, retaining the same owner across an in-process engine restart when conversations should survive. Scripts receive the actual prompt, working folder, result kind and stop signal; responses still pass the engine's result parser. Git, SQLite, checks, scheduling and delivery stay real. Use controlled release signals for held callbacks and let them finish on cancellation: stop waits for their effects to end. This fixture does not prove ACP transport, native session loading, streaming, permissions, browser behavior or process cleanup; use the native fake agent for those contracts. Its runtime factory cannot be serialized into child settings. The check-workflow fixture composes the same acceptance replies and explicit release events; `checkContext` inspects real Git/check evidence directly, and `plannerCheckpoint` stops before any working copy. Use those focused fixtures when later workflow stages are irrelevant.
- Fake agents get no browser by default, and in-process scripted sessions reject browser startup. A native-agent test that checks browsing, capture folders or report pictures opts in with `makeWorld(name, { browser: true })`, `EngineOptions.browser` and `browserTempRoot`, or the harness's `--browser-root`. Its short private folder comes from `testBrowserRoot()`, inside the runner's browser folder; pass the same folder to every engine, browser and recovery of the fixture, and remove it afterwards.
- Compare a fixture's paths with the product's in the product's canonical spelling. On Windows, Bun's `realpathSync` keeps a short name such as `RUNNER~1`, while `realpath` from `node:fs/promises` and `realpathSync.native` expand it. `testBrowserRoot()` returns the native form.
- Use the fake agent's default plan for parallel reviewers. Its short plan has one reviewer. A fixture that holds agents must still let the Check finder finish.
- `waitFor`, `until` and `waitForFile` already apply the machine's `SLOW` factor. For producer-owned readiness, use `waitFor(check, description, ms, { during: operation })` or `waitForFile(path, { during: operation })`: missing progress fails when its producer finishes or rejects. `waitFor` also bounds a pending asynchronous predicate and clears its timer/subscription on every outcome; the caller still owns cancellation and cleanup of that predicate's operation. Stretch hang-catching limits under contention; do not stretch assertions about an actual timing guarantee. Prove ordering by recording the actual completion events; a fixed number of event-loop turns is not evidence that work remains pending.
- To check a timed engine wait, such as a full model's retry, hold it from the moment the engine records it, check the delay the engine chose, then end it (`model-capacity.test.ts`). Do not try to catch the task's status before the real timer ends: with parallel peers, the task waits only once every peer has finished. Waiting to reach a step deep in the workflow covers every step before it, so give it the whole task's allowance.
- Restart tests wait for the engine to record activity, not just for the fake agent to mark itself working.
- When asserting persisted state, stop the fixture's engine before opening another writable Store. A state notification does not mean its SQLite writer has released the database.
- Before removing fixture files, await `Engine.shutdown()` for engine-owned work or `AgentRun.stop()` for a directly owned agent. Engine shutdown also settles tracked background and review-copy cleanup. Native stops can pause agents while inspecting their programs; a test ending mid-stop can leave them paused. Keep the subject’s cleanup assertion separate from the fixture’s independent cleanup.
- Manual Engine fixtures reuse `test/fixtures/direct-drivers.ts`. Register setup through `prepare` before opening a generation. Register returned helper operations through `run`, binding the current Engine when called. A restart belongs to root `prepare`, stops the old generation, then opens its replacement; registering it on the generation it stops would deadlock. Keep `setupWithCleanup` outside `prepare`, so rejected setup settles before cleanup waits for it. A cleanup wrapper alone does not own work. `close` settles every generation and confirms root removal.
- Other manual effects reuse `FixtureOperations` from `@petrina/test-support/fixture-operations`: register before starting, close admission to native effects still waiting on setup, stop existing handles and settle operations, then dispose. Shared repository cases use `withRepositoryRecords` from the engine's `test/fixtures/shared-records.ts`; its callback owns setup, Git, SQLite and the complete case. Register manual work against its actual Engine generation; stop the old generation before opening a replacement. An aggregate rejection does not join its remaining native peers; use the existing `completeAll` where those peers must all finish before returning failure. Never suppress an unexpected operation rejection to permit cleanup. Rejection or uncertain settlement retains resources; best-effort removal alone does not confirm disposal. Controlled expected-error tests independently confirm every native effect before removing their retained root.
- Use Core's `commandInputText` when a form or fixture feeds literal arguments into `parseCommand` or `setProductChecks`. `commandText` formats display and recorded identities; its JSON quoting is not the input parser's grammar. Keep execution arguments as arrays where no text input boundary is being tested. Generated fixture programs should resolve their private config files from their own script location when possible, so nested isolated roots do not repeat long paths in bounded command inputs.
- Cleanup actors must not self-expire: disappearance caused by their own deadline cannot prove the subject stopped them. A process-cleanup counterexample needs independent fixture ownership when the subject deliberately cannot confirm cleanup. Wrap every long-lived Bun actor with `@petrina/test-support/process-lease` before it starts children and close the lease in `finally`, including failures before readiness or PID capture. Its private loopback lifetime also ends actors when the worker dies; it does not signal saved PIDs or turn the subject's uncertain cleanup into success. Native handles still own directly started programs. This cooperative lifetime cannot stop an actor that is paused or ignores its connection; those native controls need their own independently verified cleanup.
- Stop-sequence tests that require complete cleanup script their process lists from the fixture's own processes, their parent links (or process groups, for the final look after a forced stop) and successful signals (`agent-lifetime.test.ts`): a native list can answer after the stop's read allowance, which rightly reports cleanup incomplete. Read natively to verify after the stop. Native lists inside a stop keep their own cases: the stop with no work, the unpaused failure control and the final look at an uncollected agent.
- Tests requiring a particular tool must wait for its readiness check to finish; another Ready tool can be admitted while that check is still running.
- Change a running fake GitHub through its shared update helper, so simultaneous readers retain one consistent answer. Its callback stays synchronous: read Git values before it.
- Publish complete JSON records with `@petrina/test-support/fixture-json`, which keeps an old reader's complete version intact until the new version is published and removes staging files on failure. `Fakes.scenario`, `makeWorld().setScript` and the GitHub stand-in use this same writer. Keep each fixture private; atomic publication also matters between a single test and its own child agents.
- Test-owned Git gets `testGitEnv()`; the Git helpers apply it unless given their own environment. Environment cleanup alone does not remove inherited push protections.
- An `execFile` stand-in that reports a successful process-list read returns `finishedHelper()`: a reported success counts as a list only once the helper's output ended, and Bun's unstarted `ChildProcess` throws when its output is read. Report only after returning it, as a real helper does: a synchronous report reaches the reader before its helper exists and counts as unreadable.
- After local delivery the working copy may be removed. Read the delivered commit from the product clone using the task branch.
- Engine helpers can be imported by standalone Bun diagnostics outside the checkout. Do not register test-runner-only hooks, such as time limits, at import time in those helpers.
- With asymmetric matchers, Bun's `toMatchObject` can overwrite checked fields. Use `toEqual`, or check a copy.
- For rejected operations use `expectRejection` or `rejectionOf` from `@petrina/test-support/rejections`. These await ordinary Promises before asserting; Bun's `.rejects`/`.resolves` matchers re-enter the I/O dispatcher and can lose subprocess or pipe notifications ([upstream issue](https://github.com/oven-sh/bun/issues/33261)). Keep the same error, message and type assertions.
- Derive verifier counts from the bounded panel: at most two initial voters from the ready tools, plus one third answer when both say a finding does not block and three or more tools were usable. Do not assume one voter per ready tool.

`bun run test:conventions` parses test source and rejects direct production Engine, EngineClient and `runChecks` imports, including package aliases, normalized relative paths and extensionless imports. The fixtures' own production imports are the only exceptions. It rejects Bun promise matchers in every Bun workspace, exclusive test selection across all workspaces and synchronous child calls in all test code. In Bun workspace tests it rejects calls to the fixtures' asynchronous helpers, their aliases, local wrappers and local async functions that nothing awaits, returns, collects or hands to a helper declared to take a Promise before using the value, and asynchronous callbacks given to callers that never wait (assertions, array tests, engine announcements, locked stand-in updates). It follows names bound once in a file, not types: work returned through object properties or callbacks given to other APIs is not followed. The guard does not prove that arbitrary subprocesses are isolated: review test-owned commands, writable resources, cleanup and native opt-ins as part of the change. Do not bypass the guard with dynamic or generated code.

## Desktop and demo fixtures

- happy-dom defaults to 1024px, where the inbox overlays the board. For a docked-inbox test, set a viewport of at least 1200px inside `act()` and restore it afterwards.
- Set focus explicitly when simulating an outside click; happy-dom's click helper does not reproduce browser focus behavior. Keyboard events alone do not produce a browser's automatic clicks; use a headless browser for those interactions.
- A task card's invisible `.card-open::after` layer owns its click area. A positioned control above it needs its own click handling.
- Demo builders cache by time. Reuse a fixed time in tests. `createDemoState` has no Analytics work log; use `createDemo` with its log, open work, quirks and triggers when testing Analytics.
- The portfolio demo uses different task IDs; locate cards by visible text or state. Stop the demo clock for stable captures; pausing the pool still lets active steps finish.

## Browser and native-tool checks

The engine can serve the built app: `bun run build`, then start it against a temporary Petrina folder on a free port. A front end without an engine runs the simulator. Keep disposable data and package installs outside this checkout.

Required browser cases open real headless Chromium using the provisioned build from the locked Playwright dependency. Install it with `bun run test:install-browser` (Linux system libraries: add `--with-deps`). The production browser deliberately ignores `PLAYWRIGHT_*` overrides, so provision the standard cache without `PLAYWRIGHT_BROWSERS_PATH`; the runner links that binary cache into its private home. Missing binaries fail rather than downloading or silently skipping. Additional native Chromium cases require `PETRINA_BROWSER_CHECK`; a default passing suite does not establish those additional checks. See the browser and capture tests under `packages/engine/test/` for the relevant cases.

When changing a connector, also verify the installed tool's model/effort selection, existing login, resume/load and a real headless page interaction. Opening ACP alone does not prove browser execution. Check new, resumed and replacement conversations, capture names/locations and cleanup. Report an unavailable browser or sandbox check as incomplete. Stop all verification processes.

Claude Code's Mac sandbox can refuse `ps`, even when local test servers work; its session settings cannot grant that access. Agents rely on Petrina's own checks for the full engine suite. Installed connector/SDK sources can be inspected in Bun's package cache rather than downloaded again.

## Required extra Linux validation

`validation run` supports only an engine-owned local Linux container on a Mac or Linux host; other hosts are refused before queueing because this path requires owned process groups. Prepare an image locally with the required tools first (for this repository: Git, Bun and Node 22); Petrina never builds or downloads images. Image preparation is an ordinary coding-tool action under that tool's permissions. The container gets a standalone one-commit Git copy mounted read-only at `/petrina`, not a linked working copy. Its command should make a writable clone inside the container before installing packages and running the full configured suite, keeping normal worker counts, assertions and deadlines. Setup and execution share the existing check time limit. The reply and evidence name the exact commit/tree, image ID, container platform and host; do not claim x86 GitHub-runner parity from arm64 Linux evidence. Full configured product checks remain mandatory for delivery.

Focused manual Linux process-cleanup tests in containers also need an init/reaper: Docker's `--init` forwards signals and reaps child processes. The owned full-validation path already sets it.

Report timings with the actual OS/architecture, CPU quota and VM CPU allocation where applicable, and keep Linux VM and Mac host load observations separate. `fixtures.SLOW` reads `os.loadavg()` in the OS running the fixtures, so a Linux VM's reading need not reflect a busy Mac. Use focused timing probes; never run competing full-suite comparisons.

The default extra-validation regressions use a private stand-in container service, immutable fixture seeds, independent writable repositories and explicit release signals. Real-container controls opt in with `PETRINA_CONTAINER_CHECK=1 PETRINA_CONTAINER_IMAGE=<prepared-local-image>` and run `test/extra-container-real.test.ts` through the engine test runner. These tiny controls require local container and process-list access; they never run a full suite or prepare an image. They verify Git identity/read-only copies, a writable clone under a different user, cancellation, timeout and recovery after an abrupt engine stop. Report unavailable native controls as incomplete.

## Manual platform checks

Use these when changing first run, desktop ownership or terminal takeover; they supplement automated coverage, not undocumented claims about every platform.

- On an installed Mac app launched from the Dock, verify login-shell PATH discovery, initial tool status, the first Planner, offline GitHub behavior and startup times. Target under 60 seconds from first opening to the Planner; an unavailable GitHub connection should add no more than about 30 seconds while planning from the local clone. First run must not trigger Documents/Desktop/Downloads permission prompts or Apple's developer-tools installer. Guide links open in the user's browser.
- On Windows and Linux desktops, verify platform-specific installation guidance, clone discovery, pasted paths and external guide links.
- On Windows, verify takeover with Windows Terminal and with the PowerShell fallback; accented paths; npm-installed tool launchers; normal exit and closing the window; concurrent copied commands and Reopen terminal. Only one tool instance may open and hand-back must wait for it.
- On macOS or Linux, a launcher diagnostic can import `launchPlan` from `terminal.ts` and run the generated script with `sh` outside the checkout. It avoids executing a freshly written program directly, which macOS may hold for first-run checks.
