# Safety boundaries

Describes existing boundaries and their limits; this is not a second policy layer. Back to [design overview](../design.md).

## Security model

Agents start with full permissions inside their own working copy; the coordinator asked for that, and it keeps the squad fast. What stops them doing harm is layered, and it is important to know which layer is the boundary:

| Layer | What it guarantees |
|---|---|
| **The tools' own checkers** | Claude Code's Auto mode, Codex's Auto review and Grok's auto mode decide what is safe to run; Codex also keeps its own workspace sandbox. Petrina does not second-guess them or re-implement them. Grok starts with `--permission-mode auto` and session auto mode, never an always-approve flag, so a saved always-approve setting does not replace the checker. |
| **Claude Code sandbox** | Claude Code's own sandbox, which Petrina only asks for (see [Permissions](agents.md#permissions)). It covers commands and the programs they start. It limits their writes to the working copy, the temporary folders, package download caches and sign-in caches, plus the product's shared git history and whatever Claude Code settings add. It does not limit reading, so logins on disk and in the keychain stay readable, and the network stays open. Claude's own file-editing tools, hooks and helper programs are outside it: their edits outside the working copy are judged only by Auto mode. Claude Code can rerun a command outside it when Auto mode approves, which SSH and headless browsers on a Mac always need. Agents still run as the coordinator's user. Where it cannot start, the agent runs as before and its session says so. |
| **Logins** | Agents act with the coordinator's own logins: they get the coordinator's normal environment with nothing stripped but the programs that ask for a password, so gh's login, git's credential helpers as configured, SSH, AWS (the aws CLI, `~/.aws` and its SSO caches), the Azure CLI (`~/.azure`) and Azure DevOps (`az devops`, and git to dev.azure.com and visualstudio.com through the coordinator's credential manager) all work. Only prompts are switched off, so nothing hangs or opens a sign-in window: git's terminal prompt and its password programs (`GIT_TERMINAL_PROMPT=0`; `GIT_ASKPASS` and `SSH_ASKPASS` removed, `core.askPass` empty), gh's (`GH_PROMPT_DISABLED=1`), Git Credential Manager's, the Azure DevOps helper (`GCM_INTERACTIVE=never`), and ssh's (`SSH_ASKPASS_REQUIRE=never`); windows stay closed (`BROWSER=none`, `PETRINA_AGENT=1`). A saved login works; a missing or expired one fails, and the coordinator renews it in their own terminal. Agents can therefore read and, in principle, write GitHub and the coordinator's other accounts. Every agent's instructions say to read and investigate freely and never to push, open, merge, close or comment on pull requests, create releases or change anything on GitHub, nor publish, merge or change other shared resources unless the task asks for it. That rule rests on those instructions and the tools' checkers, not on Petrina. |
| **Petrina publishes** | Petrina publishes deliveries with its own code, never a shell: it pushes the exact tested commit and opens the pull request, sets a release's version in a commit of its own that it checks, pushes the default branch and the new tag together and creates the release on that tag, or advances the approved local branch and pushes it. No agent works at delivery except the read-only Release Manager, which only writes a release's notes. It has no merge, force-push or delete. Titles, descriptions and release notes stay text. |
| **Petrina's own git steps** | Never run hooks or the file monitor, whatever an agent wrote into the repository's settings. Only fetching, pushing and gh use the coordinator's normal git and GitHub setup, and only right after the repository's own settings pass an allowlist, so a credential helper, SSH command, address rewrite, proxy or include an agent planted stops them. Fetches and pushes name the address saved when the product was added, never a remote, so a changed remote or push address cannot redirect them. Pushes are never forced and carry only the refs Petrina names: no tags followed, no submodules. gh runs from a neutral folder, pinned to the product's repository. Each product's credentialed steps run one at a time, the update before a delivery included. Everything that touches a working copy, the product's checks and the repository's commit hooks run without credentials. |
| **Gates** | Plan, design and delivery checks live in the engine and decide what Petrina itself publishes. No agent's answer can skip them or grant permission to publish: that is the coordinator's approval, or the task's own setting to deliver without asking, for the approved change, delivery mode and destination. They do not stop an agent that disobeys its instructions from using the coordinator's logins directly. |
| **Read-only roles** | They run in the tool's automatic mode too, so they could change files: every change and commit they leave behind is undone when their stage ends, however it ends. What the coordinator changed while driving one is kept. |
| **Take over in the terminal** | Not a Petrina boundary: it is the coordinator acting with their own setup and logins, in the tool's normal mode with its usual prompts, where some actions may run without a prompt. Petrina adds no blocks there and does not change their GitHub access, connectors or plugins. It only keeps credentials, its engine key and its own variables out of the launcher, its command lines and the terminal, and makes sure delivery through Petrina still goes through review. |

Known limits: anything done in a take-over session (a push, a pull request, a connector action) happens for real without Petrina's review, and Petrina does not notice it; someone can also reopen the conversation by hand in another terminal after handing back, and Petrina only tracks the sessions it opened. Agents run as the coordinator's user and act with the coordinator's logins.

"Never publish without approval" for agents rests on their instructions and on Claude Code's, Codex's and Grok's own checkers; Petrina's gates decide only what Petrina itself publishes. Saved logins, settings in the home folder, Petrina's own connection file and its approval controls are only as protected as the tools' checkers keep them. Petrina adds no operating-system boundary of its own. Claude Code's sandbox limits only where commands write, and is not a hard wall: Auto mode can let a command out.

In a linked working copy it lets commands change the product's shared git history (create, move or delete its branches and tags). Claude Code merges Petrina's write list with the coordinator's own and the product's Claude Code settings, which can widen it, and an organisation's managed settings outrank Petrina's. Codex's own sandbox may still block some logins (writing aws or az caches, say).

## Security notes

- Agent output is untrusted. The UI renders prose as text (no HTML, no `dangerouslySetInnerHTML`) and report pictures from validated task storage. Links are opened only when they are `https://` and only through the host.
- Petrina runs each product's checks itself, outside the tools' safety checkers (see `AGENTS.md`). Reviews, the tamper check and the review guide compare against the base commit pinned when the working copy was made, never a ref an agent could move.
- Agents get the repository's content as context. Treat it as untrusted input to the model: approval gates and permission decisions are enforced in code, not by prompting.
- Every result from an agent is validated against a schema before it changes state. IDs coming from agents are validated before use.
- Round limits and time limits cap every loop.
- The window has a strict Content Security Policy and only the Tauri permissions it needs.
- CI uses read-only permissions and actions pinned to commit SHAs.
