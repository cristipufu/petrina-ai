# Repositories and delivery

Owns source resolution, working-copy lifetime, publishing and delivery recovery. Back to [design overview](../design.md).

## Working copies

- A task can work on several products. New task records the coordinator’s choices, with a starting point and delivery mode for each. The planner receives the registered products and proposes a structured list with reasons; Petrina validates it rather than interpreting the task’s words. Shared tasks always need a plan check. Unregistered repositories can be added there, with their permanent folders confirmed before approval. Coordinator-selected products remain until the coordinator removes them.
- Planning runs in a separate planning folder, before any task working copy exists. A changed proposal, or a resolved PR destination, needs the coordinator's confirmation in the plan check. Ordinary unchanged default-branch tasks keep their optional plan check. Branches and PRs are validated read-only on GitHub first; fetching task content and creating the working copy wait for confirmation.
- Each involved product saves its repository identity, saved address, resolved source, delivery mode and exact destination independently of product defaults. A PR also saves its actual working repository and branch. Named branches fetch from the saved product address; PRs fetch through that repository's PR head reference, including forks. Failed explicit-source fetches wait for Retry. The initial commit stays recorded separately from later source updates.
- PR background is read outside working copies, using `gh pr view --repo` and fully paginated API endpoints naming that same repository and PR. It includes review summaries, discussion, file comments and replies, with authors and locations, and checks with their versions and states. Its read time is saved. Every later agent step, repair round and resumed conversation gets refreshed background; a failed refresh stops the step without replacing the accepted design or notes.
- Repository loops enumerate stable `RepositoryContext` handles through `scopesFor`; an empty unapproved product map has no execution scope, and excluded repositories are visited only when explicitly requested for cleanup.
- Each task gets a git worktree in Petrina's data folder (not inside the repository), on a branch named `petrina/<task-slug>`.
- Git operations retain native SHA-1 or SHA-256 object IDs, including abbreviations where accepted. An invalid saved version or failed comparison cannot establish that a product is unchanged. A failed reset remains an error; read-only cleanup never reports that commits were removed after a reset failed.
- After a verified local delivery or release, cancellation, or GitHub confirming a pull request was merged or closed, Petrina removes the working copy and everything inside it, including parallel reviewers' copies and their Git records. Startup catches reviewer copies left by a crash even when the main task copy was already removed. Branches and saved task history stay. An open pull request keeps its copy even when cancelled; an unanswered GitHub check keeps it too. Removal waits for the agent and its programs to stop, takes no agent slot, and never fails the task. The timeline records removal or one readable reason for retrying. The once-a-minute checks retry failures, and startup catches up on older finished tasks across products.
- Slugs are generated by Petrina from a strict allowlist (`[a-z0-9-]`), never from raw task text.
- Processes are started with argument arrays, never through a shell.
- Petrina gets every delivery ready and publishes it itself (see Delivery). No agent publishes, and Petrina never merges.

## Delivery

- Delivery follows the task's approved source. A PR start adds the task's checked commit to the original PR's actual working branch, using the confirmed fork address where applicable; it creates no replacement PR and edits no title, description or comments. Branch starts either open a PR into that branch or advance the local destination and push it to the saved product address. Commit to main likewise advances main and pushes it. Releases use the resolved default branch; incompatible starting choices require correction.
- Source updates use the latest approved source before the delivery check and again before publishing. PR updates use their working branch, never their target branch. Existing source commits remain intact. Conflicts return to the existing builder conversation, checks and review. A deleted source, closed PR, replaced history, unavailable fork or refused push preserves the work and stops further publishing.
- Local destination updates and their pushes have separate saved evidence. Recovery confirms that the exact tested commit reached the approved destination, even when newer commits followed it. An existing PR alone is not evidence of a successful update. A completed local update with an unfinished push stays visible.
- If GitHub gains source commits after a local update but before its push succeeds, preparation carries the task onto them and checks it again. Only the exact unpushed commit placed by Petrina may be replaced in the local destination, with the earlier source commits preserved. Newer local commits, uncommitted work or a destination checked out elsewhere stop that replacement and preserve the work.
- After review, and the delivery check when the task asks for one, Petrina makes sure the work is still what was approved: an approval holds for the approved change (its fingerprint), delivery mode and destination, and anything else asks again. It brings the one commit up to date with the latest approved source (freshly fetched from GitHub before publishing; if that fetch fails, Petrina publishes nothing and waits for Retry) and runs the checks on it.
- Then Petrina gets the delivery ready itself. A pull request's title is the builder's commit title. Its description is the builder's: the builder writes one for every pull request delivery and keeps it current in fix rounds, and when it has none Petrina writes one from the builder's report, so a missing description never holds a delivery up. Petrina adds its own part under "Checked by Petrina", saying only what it saw: the acceptance checklist (ticked only where a tester checked it), the checks it ran on the commit, who reviewed it (role, tool and model) and the follow-ups older than the change. Text past GitHub's limits is cut. "Commit to main" needs nothing more.
- For a release Petrina works out the version (the latest release plus the product's bump, or the version files' own for a first release, or 0.1.0) and sets it itself, as one version commit on top of the work: in the product's main version files at their usual places (package.json and Cargo.toml at the top, tauri.conf.json at the top or in src-tauri), changing only the version, and in the product's own entries of the Cargo.lock beside a Cargo.toml. It then checks that commit: it changes only version files, and only their version, and every main version file says the new version. A file it cannot set or read stops the delivery with a plain message and nothing published. Main version files that do not follow the latest release stop for the coordinator. The checks run again on the version commit. Subfolders and other files are the reviewers' to check.

### The Release Manager writes a release's notes

It is the only agent at delivery, and only for releases. A release ships everything on the default branch since the previous release, from many tasks and agents, so its notes must cover all of it, which no builder knows. Petrina gives the Release Manager every commit from the previous release's tag up to the commit that ships, this task's included, each with its message (a task's commit carries its title, its summary and what changed for users); for a first release, every commit there is, the 200 most recent at most, saying so. It hands back only the notes, for users, grouped and in plain language. Petrina checks they are there and fit GitHub's limit, through the usual fix-your-result loop. It is read-only: anything it changes or commits is undone. Pull requests and commits to main need no agent: the plan's delivery step stays where it is and runs none for them.

- "Failed" publishes nothing in any mode: the version change goes, and the task goes back to the builder, review and the delivery check with a blocking finding. After two failures Petrina stops and asks.
- Petrina then publishes the exact tested commit: it pushes the task branch (never over other work already there) and opens the pull request; or pushes the default branch and the new tag in one all-or-nothing push, refused if the tag exists, and creates the release on that tag, only once GitHub shows the tag at the tested commit (Retry and "Ship it again" included); or fast-forwards the local approved branch, only if it is still where Petrina saw it, and then pushes that branch to the saved GitHub address (never forced: if GitHub's branch has commits this computer does not, the push is refused, Petrina brings the work up to date, runs the checks again and retries, and the task counts as landed only once the push is through). Meanwhile it holds git's own lock on the main copy's staging area, so the main copy cannot switch branches halfway; if it switched just before, Petrina refuses and changes nothing. If the approved source moved before a delivery goes out, Petrina brings the work up to date again, runs the checks again and, for a release, sets the version again and has the notes written again from the new list of commits (three times at most). Pull-request preparation also uses the latest approved source.
- Each step is saved before it starts, and each product's credentialed steps (fetches, pushes and gh) run one at a time. Pause and cancel are checked when a step actually starts, not when it joins the product's line. Before reporting success Petrina checks the result on GitHub or in the main clone. Interrupted deliveries go through the one check under "Shipping is never repeated blindly".
- Fetches and pushes go to the GitHub address saved when the product was added; an old HTTP or git-protocol address uses HTTPS for the same GitHub repository, without changing the clone's settings. For a product added before Petrina kept it, the first step that needs it shows the current address once and asks whether it is the product's; the answer is kept. After a "No", Petrina does nothing for that product that needs a login; "Commit to main" still works, without the push.

## One commit per task, on top of the latest approved source

After every build Petrina folds the branch into one commit on top of where it forked, under the builder's title in the repository's own style, so the repository's commit-message rules see what will land.

Right before the delivery check, and again right before it gets the delivery ready, Petrina puts that commit on top of the latest approved source itself (the PR’s working branch for a PR start, and both the local and GitHub destination for commit delivery), with `git merge-tree` and `commit-tree`, which never leave a working copy halfway through a rebase (`packages/engine/src/update.ts`). Clean: the checks run on the result, and the delivery check shows it.

Overlapping: the working copy is put on main with the change applied, conflict markers and all, and the builder brings it up to date (it learns what main changed from its commits, ports the change, leaves no markers, runs every check). The same happens at the start of every review round, so a conflict is found before any reviewer spends time and a port after a review stays the exception.

A conflict-free update preserves compatible reviewer conversations, separately for each seat, including when only a companion product moves. Reviewers receive their saved and current bases and the current comparison and review guide; the carried incremental comparison alone cannot cover incoming main changes. A conflict port discards those conversations with a stated reason. Replaced or diverged source history still stops the update. Checks run on the updated code before reviewers start; conversation reuse changes no evidence or delivery gate.

When a port does follow a review, the change itself was reviewed already: one reviewer, on a tool other than the builder's where the stage has one, reviews only the port (`git range-diff` between the reviewed version and the ported one, and each resolved file against main's), as one round; its findings go back to the builder as usual, and the rounds after it are ordinary. The coordinator's approval still resets after a port, because the change was rewritten by hand.

Prepared port material contains those port comparisons rather than regenerating the complete reviewed change. Lockfile comparisons are linked separately and retain their review scope. Each repository's temporary review copies are removed through that repository's own clone, including copies for products removed from the task.

Every repository keeps its detached review copies under its own product directory. Review setup, saved screen turns, image previews and cleanup use that same location, so one product's cleanup never removes another product's folders through the wrong clone. Shared starting-point validation reads independent product rows together, then applies duplicate checks and approval decisions in proposal order; replies from a superseded proposal are ignored.

Nothing at delivery rebases, merges or changes code; for a release Petrina adds only its own version commit. Petrina delivers the result itself, as a fast-forward, a pull request or a release.

## Shipping is never repeated blindly

Petrina publishes, and saves each publishing step before it starts. One check runs before Petrina publishes, and again after any interruption (a quit, a crash, a pause, a failed step and its Retry, a cancel): it checks whether the tested commit reached the approved PR or branch, the release on the saved tag at that commit, or both the local destination and its push. A completed local update is recorded separately from its push; newer destination commits do not hide completed delivery.

Releases published before this delivery started never count. It asks GitHub about the product's own repository, from outside the working copy, so a remote an agent rewrote cannot fake a delivery, and it first makes sure the login can see that repository: GitHub answers "not found" alike for a missing release and a repository the login cannot see. Found: it is recorded.

Clearly not there: Petrina carries on with the saved step; pushing the same commit again overwrites nothing, and GitHub refuses a second open pull request for a branch, a second tag and a second release. GitHub unreachable, or something else there: Petrina publishes nothing more on its own and the coordinator decides ("Check again", "Ship it again", which gets it ready again and still runs the check, or "Mark as done").

A cancelled task stays cancelled, but what went out keeps its link; if GitHub cannot be asked then, Petrina asks again every minute and after a restart. A delivery saved by a Petrina from before this design, whose delivery agent published it itself, is never acted on by Petrina: no check, no update from GitHub, no preparation.

The task shows "This delivery was interrupted before Petrina was updated: check GitHub, then choose", with "It went out (mark as done)" and "Ship it again" (a fresh delivery, from the delivery approval as the task sets it), and nothing happens until the coordinator picks one. Cancelling it keeps the note on the task.

## Tasks across products

One task has one queue position, plan, design, acceptance list and delivery decision. Each product retains its own approved source, working copy, Builder conversation, checks and delivery. State ownership and historical membership are defined in [state and usage](state-and-usage.md#tasks-across-products).

### Scope and preparation

The coordinator may select several products, or let the planner propose them. The planner receives the registered products and existing choices, can investigate GitHub with the coordinator's login, and returns explicit choices and reasons. The engine validates those choices; it does not infer repositories or destinations from task wording. An omitted coordinator choice stays visible until the coordinator removes it. A PR fork remains a starting point within the original product.

The complete product list is approved before fetching, cloning or preparing copies. A proposed repository needs a confirmed name and permanent folder. A separate task copy keeps that permanent clone on its default branch. Preparation is saved per product; retries preserve successful preparations and reuse only Petrina's saved clone folder. A resumed clone must still point to the approved repository; another repository’s files and metadata stay untouched and require a different folder. If the repository changes its default branch, preparation still uses the approved branch when it exists, including as an origin-tracking branch; it never switches the approved source. A different folder or revised scope keeps the rest of the plan.

### Building and review

There is one Build step. Each product has an owner working in its own saved conversation, with the full product map available to read. Editing roles work product by product before final review. Reviewers inspect independent snapshots of all repositories at the same saved versions. Product checks, commit hooks and the deleted or skipped tests check run separately per repository. Missing evidence says Not run.

### Repairs

Every failed acceptance item and review finding names its affected products. Repairs visit the lead first when affected, otherwise plan order, and then every remaining affected owner. Each builder sees only its own items and answers separately. A shared finding stays open until every owner has answered and combined verification confirms the repair. An unassigned item stays under Together for the coordinator. Builder answers never replace acceptance evidence. A shared item records every affected version; changing one invalidates its evidence. Each product has its own check repairs, two per failure episode until its next genuine pass, and two acceptance repairs, saved across restarts. Visiting several owners is one repair pass. A check repair visits only products whose checks fail; Petrina's other findings, such as a deleted test, go through review. A check repair started at the delivery check or right before shipping returns through the first review after the Builder, then acceptance and the delivery check, like a single product; once a product has published, the rest returns to shipping as before.

Review objections and shared repair decisions wait until every reviewer has reported, then settle before Petrina decides whether a voter is needed. A confirmation that the problem remains keeps it open, whichever report arrives first, including across a restart. An exhausted product keeps its unresolved failures for the coordinator while other affected products use their remaining tries. Before review, empty product sections and Together say reviews start after the build; during review they say no findings have been reported yet. Once all planned reviews finish without findings, every section says every reviewer passed, including at delivery approval, while waiting for merge and after completion. An empty findings section alone never proves that the combined review passed.

### Publication and landing

One shared delivery approval covers all repositories and the companion wording. When a pull request will receive companion text, pending links name their approved owner/repository; the preview explains that every companion PR’s readers will see all companion names and links. Deliveries with no publishing pull request omit that wording, since releases and local commits do not receive companion text. Petrina fills in the resulting PR or release addresses within those approved repositories automatically, without another checkpoint. Changed destinations still require renewed approval. Release versions and notes are previewed as text; version commits are made and checked afterwards. All repositories finish publication preparation before the first publication. Existing PRs keep their title and description and receive one companion comment. New PRs link to confirmed companions; linking is saved separately from publication. Retry checks uncertain outcomes first and resumes unfinished work. Confirmed publications are never repeated or rolled back.

The task lands only when every published repository has landed. An open PR keeps it Waiting for merge. A PR closed without merging requires an explicit coordinator decision and keeps dependents blocked. Removing a finished product preserves shared history under the remaining products; removing its last product removes the task and its embedded history.

The regression cases live in `packages/engine/test/repositories.test.ts` and the source, review-settlement and delivery tests. Historical acceptance checklists are retained only in [the archived brief](../archive/shared-tasks.md).
