# Workflow and review contracts

Owns stage progression, Backlog, acceptance and review decisions. Back to [design overview](../design.md).

Required extra container validations record separate version-bound evidence on the requesting journey step and never alter configured check gates, findings, repair returns, acceptance or approvals.

## Stage kinds

| Kind | Behaviour |
|---|---|
| `do` | One role on one profile produces its result |
| `converge` | Author and reviewer (different profiles) alternate until the reviewer has no open blocking objection, or the round limit is reached and the coordinator decides. The settling review's non-blocking points stay noted and go to builders as [advice only](agents.md#final-design-review-notes), never as requirements, acceptance items or blockers, and with no extra design round |
| `review-chain` | Petrina's tamper check and the product's checks first, then every reviewer at once, each on its own, then fresh agents voting on Important findings. Important findings that stand send the change back to the builder as one list, then the review runs again on what changed: within the planned rounds, and past them while each round resolves at least one previously open Important finding, up to five. A round that stops making progress goes to the coordinator, whose delivery check then says "your call" with the count still open |
| `do` with the Tester | The product checks run first, so the Tester can reuse verified automated evidence and focus on trying the acceptance list like a user, once on the change before its first review. Each item is pass, fail, or could not be verified; an unavailable required check stays unverified and waits for the coordinator's delivery decision, even with delivery approval off, without being sent to the builder as a product defect ([required acceptance](#acceptance-evidence)). Fix rounds skip it (the code reviewers check the fixes), and right before the delivery check the tester tries the final code once more if it changed since, or an explicit proof request needs current-version evidence; a reproduced failure there goes back to the builder like a failing check. Failed product checks return to the builder while their failure episode has returns left, then ask the coordinator immediately; no Tester starts while those checks fail |
| `gate` | Waits for the coordinator (design approval, delivery approval) |

Each new acceptance pass or failure records a short account of the actual scenario and observed result, or names the applicable current automated evidence. The node's details show only the acceptance evidence recorded for that step; task-wide marks and nearby steps supply no replacement. Automated checks and reused command evidence establish no acceptance verdict. Missing evidence remains unavailable rather than passing or creating a product defect. Previously finished records keep their original evidence without invented detail. Builder repair details name acceptance failures only from their recorded triggering Tester, excluding unavailable probes. One probe may support several items; this adds no duplicate full-suite run or workflow gate.

Agent verification instructions require a real execution deadline through the harness or an external parent process, with owned background handles retained and stopped. A tool's output wait is not a command deadline, and a program can starve its own test timers. This uses the tools' existing command controls; it adds no process scanner or memory sandbox. Engine-run product checks keep their separate external deadline, complete logs and process cleanup, and legitimate full-suite budgets are unchanged. The [shared-host load rule](../testing.md#shared-host-load-diagnostics) is instructions only: Petrina reserves no capacity, monitors no load and adds no enforcement.

Builder return outcomes compare the actual starting and ending code trees, including commits made by the Builder. Commit identity and reported fixes do not establish a content change. Each return retains its own answers and investigation; reported fixes remain Builder claims until verification. An unchanged repair with unresolved checks says “No code changes; checks still failing”, without discarding earlier task changes.

Unchanged code and check definitions reuse eligible evidence. The journey records a selectable evidence handoff after the return, with the original product, execution, attempt, timing and diagnostic; reuse creates no execution or finding and spends no automatic return. Delivery decisions snapshot all supporting product evidence across intervening steps. Failed or unverified checks offer an explicit fresh check execution, original evidence, or a send-back with a note. Rerunning approves no delivery, preserves the spent repair allowance, and resumes outstanding stages after a complete applicable pass. A send-back after exhaustion grants the requested turn, without resetting the two automatic returns.

Failed or unfinished checks are marked interrupted only when recorded machine events overlap their actual execution interval. On macOS, bounded read-only power-log inspection supplies this evidence during execution, reuse and startup recovery; a timeout, long wait or Builder explanation does not. A coordinator stop already establishes incomplete verification: it skips or cancels power-log inspection rather than delaying cancellation. Stopping or restarting the engine also cancels startup inspection, retaining the original evidence for a later recovery. Keep the original reported outcome and diagnostic alongside the event and its time. Interrupted verification blocks delivery, adds no confirmed product defect and triggers no automatic repair or repeat execution solely for interruption. Missing historical timing or provenance stays unavailable.

## Task lifecycle

```
backlog → queued → planning → designing → building → reviewing → ready → done
            │            │            │           │        │
            └──── any stage can be: running · needs-you · paused · failed
```

The stage column (planning, designing, building…) is derived from the role of the current stage; the Products page counts tasks by it. The board itself is one grid of cards grouped by what each task needs (needs you, working, waiting, queue, backlog), and every card shows its own pipeline from its plan: done steps checked, the current one named, stages the plan does not have left out (`packages/core/src/board.ts`).

Static check preparation and queued/running commands hold no agent slot. Preparation is bounded by the pool size, check commands keep their separate concurrency limit (one task at a time by default), while queued planners can still use free agent slots. Check finder, reviewer and Tester conversations acquire their actual model slots before starting. A pause or drain admits neither new checks nor new conversations.

A coordinator can add a runtime prerequisite wait after work has started. The task finishes admitted work, then waits without advancing its plan, consuming a review round or repair, or resetting a conversation. A part-done review or vote retains the accepted seats and runs only its missing participants after release; it never counts as passed while incomplete. Existing plan, design and delivery checkpoints stay open and answerable, with the next new step held. The saved reason, prerequisite outcomes and change history are visible in task details and coordinator reads. A prerequisite that ends without landing requires the coordinator to revise or clear the wait with a reason. Release uses normal scheduling, source updates and all version-bound verification; see [runtime scheduling](engine-runtime.md#scheduling).

## Backlog and finished work

A backlog task is saved work awaiting the coordinator’s review. It cannot take a pool slot or start a planner. Its request, source and delivery choices remain editable; the explicit `queueTask` command puts it into the queue. Combining Backlog requests validates the whole selection before changing it, saves one queued request and the original links together, and retains retry identity across restarts. Original bodies remain in History; pictures are copied before their original bytes are removed. Only matching product/source/delivery choices and requests without unresolved dependencies may combine; approvals are never weakened.

A queued task may return through `moveToBacklog` only before it has ever started. The engine enforces both transitions, and the simulator follows the same rules. New task defaults to Backlog in the window; API callers that omit the option retain the existing queued behavior.

When a task finishes, confirmed unrelated older bugs become Backlog cards, with reproduction, evidence and links to their source findings. Independent reviewer and verifier judgments settle first; a bounded identity check then groups reports of the same bug and reuses open follow-up cards and matching unfinished coordinator-created bugs. Uncertain matches remain visibly untracked; unavailable matches keep a retry. Nits and speculative improvements create no cards. These cards never queue themselves or prevent the original task from finishing.

A reviewer naming a shown open card adds the report there. An explicit `none` keeps it off the shown cards. An omitted choice supplies no hint: the usual same-bug check considers open candidates, including any shown cards. With no candidates, a complete confirmed report from a done task opens one card. On-board reports previously left at “No card was chosen” solely for an omitted choice are reconsidered on the next pass; archived history is not scanned.

A task is never offered as the destination for its own reports, including a running card that already carries reports: its own reviewers do not see it, resumed reviewers' frozen lists drop only that card and gain nothing, and the identity check never places the task's own reports there. Reviewers of other tasks still see it, and saved assignments and historical links stay as they are. An unassigned report naming its own task supplies no hint, as an omitted choice does, and an on-board report left at “No card was chosen” only for that is reconsidered.

After filing or finding the bug themselves, the coordinator can use `task.track-finding` to record an existing bug task for a complete confirmed older report left “Not tracked”, including from History. It waits for automatic linking, accepts settled untracked outcomes (including a match awaiting retry), and rejects unfinished or cancelled sources, links not yet added to their chosen card and conflicting targets. An eligible same-card request can finish an interrupted picture copy, including a stranded History report whose original picture bytes are already gone. The target must be a different, non-cancelled bug task covering every reported product. Open targets gain provenance and copies of any original pictures before tracking is saved, preserving their request and products. Finished targets remain unchanged and are refused while original picture bytes remain. The link and request receipt save together; repeat requests are safe. No reviewer or matcher runs and no card is created. Later automatic passes leave the link alone, and it never prevents original-picture cleanup.

The card's current request describes the remaining bug; original reports remain provenance and never override coordinator edits in context or matching. Unfinished coordinator-created bugs can receive matching reports through the same identity check while they are in Backlog, queued, running, waiting, paused, failed, awaiting the coordinator or delivered with a pull request still open, at the boundary automatic cards use; only reports covering exactly their nonempty product set are compared with them. Ordinary features, different manual product scopes and finished or cancelled tasks are not candidates; a task already carrying reports, such as a combined request whose kind is feature, keeps its existing rules. Similar wording, a shared location or a tentative overlap is not identity: uncertain and unavailable outcomes keep their handling above. Listing candidates, checking the returned match and saving the link use one decision, so a request queued or started during matching stays the destination. A fix that finishes, is cancelled, changes products or leaves the board before its first saved assignment stays untouched, and the report is handled as a fresh one; reports only from unfinished tasks then wait for a later pass rather than opening a card alone. Reuse appends only report credits, reproduction, evidence, links and needed pictures: the request, title, products, starting points, delivery choices, approvals, plan, queue place, stage, repair counts, current agents' instructions and frozen review evidence stay as they were, no agent is interrupted or instructed, and no work starts. Linking a running fix records provenance, not a repair. Reviewers can explicitly report a supplied older bug as repaired with its original reproduction, current passing result and nearby controls. This settles only after the complete review group, only with saved code versions, and only when no peer still confirms it. Omission, code changes and general passing checks never imply a repair. A later current reproduction reopens the finding and keeps the repair proof as history.

Identity agents respect paused scheduling, usage limits and the ordinary global and per-tool pool caps, appear in the pool while matching, and stop with the engine. They compare only the supplied reports, in an empty temporary working folder. Matching therefore needs a free permitted agent slot and can wait, showing “The match could not run” until the retry succeeds, even when the matching fix is already running. Linking neither queues work nor prevents the source task from finishing.

Identity matching deliberately prefers high effort for semantic judgment, then medium and low when high is unavailable, with extra high last. This avoids using the deepest reasoning by default without assuming the lightest effort can reliably identify the same underlying bug.

Pictures needed by an unfinished follow-up are copied to that card before the original task's pictures are removed. The chosen card and report identity are saved before copying, for both new and existing cards. While a link and its copies are saved, the destination and every report's own task stay on the board with their pictures; finishing or cancelling either still happens, and only moving to History and picture cleanup wait until the result is saved or Petrina stops. A destination that finishes or is cancelled during the copy keeps its assignment and report evidence and is not reopened; afterwards the closed-target rules apply, so a copy that failed there leaves the original pictures to the source's cleanup. A failed copy says “Not tracked. The pictures could not be copied” and keeps that assignment, its retry and original bytes across source retirement and restarts. Combining Backlog cards explicitly transfers their reports, unfinished assignments and picture provenance to the combined task, including through repeated combinations; automatic recovery, manual linking and cleanup follow that transfer. A saved destination is never swapped automatically: the chosen card moving to History, closing or no longer covering the report does not free it for another target or open a replacement card, and a report already credited there still finishes its copies and tracking; cancelled targets remain ineligible for manual linking, and finished targets retain the original-picture rule above. Fixing or withdrawing the older report releases its unfinished assignment. Cleanup reads archived bodies only for saved pending links, rather than loading finished conversations just to remove their capture folders. Completing or cancelling the follow-up removes its picture bytes as usual.

## Maintenance completion

Scheduled tasks start directly with their saved maintenance role and profile, using the normal Queue, default-branch source, product delivery destination, pool/tool limits and working-copy lifecycle. There is no Planner turn or additional Builder.

After an accepted completed maintenance turn, compare the actual remaining product tree with its base. With no changes, retain the real report and finish in History through normal cleanup, without product checks, reviewers or delivery approval. This also applies to writable investigations and changes withdrawn during repair. Nothing actionable found is an honest report, never a replacement for errors, incomplete work or unresolved settings decisions.

Changed maintenance work remains Medium risk and runs ordinary product checks, two fresh Code reviewers and delivery approval. Reviewers prefer different available tools and avoid the maintenance profile when another tool is available; with one tool they use independent conversations. Existing finding verification, repair limits and update-conflict handling apply, returning to the frozen maintenance role and profile. Maintenance adds no Security review, risk classifier or delivery system. Agents never publish or merge.

## Checks, reviews and risk

### Check output

Each check and commit hook streams its complete output into a separate private file in the engine's data folder. The saved result keeps its exact location across restarts; state and prompts keep only a short excerpt. A builder fixing a failed check receives the file's location and reads it instead of rerunning the command to recover a lost error. A failed or incomplete log write is reported separately and never changes whether the command passed. Older runs without a log say so. Each log is created exclusively, private to the engine. Once writes settle, Petrina records through that same open file its device and file number, exact length and a SHA-256 fingerprint of its first 4,096 bytes. Because a removed file's number can be reused, diagnostic reads return the file only while it matches all of these, and otherwise the saved result; the fingerprint is bounded recognition of the beginning, not authentication of every later byte. The file itself stays the unchanged process output. Older runs without these facts, or whose capture failed, use their saved result, labelled legacy or incomplete.

Builders repairing an open product-check failure can receive up to three related evidence references. Matching requires the same product, failing command, recorded product-command list and an overlapping runner-recognised suite-qualified test name; hook inputs and commit messages do not define that match. Only completed check-specific Builder answers qualify. References name the failure and repair steps, attempt, log and code snapshots, with claimed, checked or reviewed status supported for that exact version. No reviewer text or other task context is shared. Lookup reads bounded recent task evidence and History projections, without a model comparison or a wait. Missing provenance is omitted; unavailable logs or snapshots are qualified. Cancelled, paused and superseded unlanded work is omitted. Confirmed deliveries use full identities and appear only when local repository evidence establishes that the receiving Builder's current prepared history, after normal updates, lacks them; original task starting commits never establish absence. These are navigation leads, not cause classifications, check exemptions or dependencies.

### Acceptance evidence

Review roles can return structured proof requests separately from defect findings when the plan has an acceptance-testing role (identified by its checks result). Each request records an id, the requirement and reason, affected product ids, an optional exact checklist link, requester stage/round/place, reviewed trees and the owning final acceptance stage. Invalid descriptions, reasons, products or checklist links are repaired in that reviewer's conversation before saving. Request identity is its accepted result position within a saved review execution, never similar wording. Reopening a passing review creates a new execution without spending another repair round; replaying an accepted result in that execution creates nothing twice. Missing validation alone belongs here rather than in findings or confirmations; Petrina never reclassifies an existing finding. Requests do not enter verifier ballots, spend repair or review allowances, or prevent a proof-only round passing. Mixed code findings retain their normal route. Later reviewers see only earlier requests in the round's frozen snapshot. Builders leave this proof to final acceptance.

After the last update from main and passing configured checks, an open request forces final acceptance on the exact prepared product trees, even without a brief/checklist and even when only main changed and the task patch is identical. A plan that omitted delivery approval gains a preparation checkpoint for this purpose; its existing automatic delivery choice still applies when all requested proof is current. A readable latest Tester checklist pass on exactly the reviewed affected trees may settle a linked request as already current. Otherwise the Tester answers every open request by id with pass, fail or blocked and evidence; missing/duplicate answers are repaired in the same conversation. Only the engine's recorded completed Tester step and actual versions establish proof. Reviewer/verifier opinions, Builder reports and pasted output do not. Missing evidence or unavailable platforms stay unverified and ask the coordinator, without an unchanged retry or Builder return. Reproduced failures retain the acceptance-failure Builder route and its two returns; requests stay separate from those failure findings.

The in-flight acceptance snapshot survives pause, restart and tool handoff with its saved Tester conversation. A fresh attempt without that conversation captures the newly prepared versions. An interrupted run settles nothing. A code change during testing leaves each observed outcome intact: failures still go to repair, proof for unchanged affected products remains valid, and outdated passes need final acceptance again within the normal limits. A missing platform remains unverified even after the code changes; release wording also shows that gap. Every completed run retains each product's task-patch identity as well as its complete tree. Tasks with requests allow at most two final refreshes caused only by main moving per delivery attempt, across all products together. Code-change retries retain their existing allowances. Exhaustion leaves earlier proof visibly out of date at the coordinator's decision. Only asking for changes at the delivery checkpoint resets this refresh count; returning there because publishing found a newer version does not. Tasks without proof requests keep their existing single/shared acceptance reuse rules.

When Petrina undoes commits or edits to tracked project files during an acceptance run, that run cannot verify the restored product. The cleanup that observes them (a read-only step's end, a shared task's companion products for any role, or the cleanup before a coordinator takes over) saves the fact with the run, before undoing anything, and its warning names each product and a few files. The decision follows the role's result kind and its actual permission in that step, so an editing role's permitted edits before the final review are saved as usual. Every checklist item and proof answer from that run is then saved as could not be verified: "Petrina undid changes during acceptance testing. This run cannot verify the restored product.", followed by any reason it was already unavailable. The agent's own report keeps its answers and evidence. The run stays unverified even without checklist items or requested proof, and acceptance details still select it. Restored version equality, an earlier pass or a checklist-linked request cannot make it current. In a shared task the whole run is invalid whichever product changed; items keep their earlier products and versions. Reported failures stay in that run's history: no finding changes or appears, and no Builder return or repeated test follows. Unverified acceptance prevents automatic delivery; the coordinator's decision stays explicit and version-bound. A plan that omitted delivery approval gains the delivery checkpoint for this decision, as it does for requested proof; once a later run verifies acceptance, the task's own automatic delivery choice applies there again. The fact survives a stand-in, a take-over and a restart within the run, including changes undone as Petrina quits: those are kept beside the saved state and join the same in-flight run at the next start, and a run whose cleanup had not finished, with that cleanup's own record missing or unreadable, then stays unverified, whether Petrina closed while the agent worked or after it answered. When nothing shows what was undone, its items and proof answers say so instead: "Petrina stopped during acceptance testing and could not confirm what its cleanup undid. This run cannot verify the product." A fresh run, after a pause or a failed attempt, captures its own versions, and an interrupted attempt's step keeps its record. New untracked files alone are output: they are removed as before and change nothing. Petrina cannot see edits an agent undoes itself before the step ends. Output inside a nested repository looks like a tracked change.

Required acceptance is the saved checklist and explicit proof requests; a probe the Tester adds on its own is an observation and never becomes a requirement. When a required item could not be verified, or Petrina invalidated the run, delivery waits for the coordinator even where the plan omitted delivery approval: the plan gains the existing delivery checkpoint once, and planned steps that have not run yet, such as the review, still run first. The unavailable item alone causes no Builder return, repeated test or review. Mixed results follow one rule with or without proof requests: reproduced failures, including an extra probe's, keep their repair route and two acceptance returns, and returned work is tested again while the other item stays unavailable; once failures are resolved or repair is exhausted, the decision keeps both. The decision names each unavailable item, its affected products in a shared task (or that none was assigned), why it was blocked, what the Tester tried, and whether what would ship has the same contents as tested, changed since testing or is unknown; it saves the items, the run's original report and the exact tested and prepared versions. The added checkpoint lifts, applying the task's automatic delivery choice again, only on a complete, current pass of every required item, even while an extra probe stays unavailable; the final retest before it follows the same required-only rule. Low-risk and requested-proof refusals are unchanged, and without a checklist or proof requests unavailable extra probes add no hold. Publishing starts only after the coordinator's explicit decision about that same run and its items: readiness and the last check before publishing, after recording what already went out, otherwise return to the delivery checkpoint (adding it when missing), including for prepared deliveries, retries, Ship it again, carried-over deliveries and tasks already past testing. Recovering a commit delivery whose local update finished but whose push did not keeps that update and holds the push the same way. An automatic authorization never counts, and an approval with no saved record of covering those items, such as one given before Petrina kept that record, is asked again and says why. Approval ships with the gap recorded: the items stay unverified, and a pull request's acceptance checklist says Could not verify, unticked. Asking for changes clears that decision and tries the items again.

Every delivery decision on a task with proof requests saves the complete product trees and all request statuses shown, including automatic decisions. Publishing rechecks those exact versions and statuses after fresh preparation, including across restart. A different shipping version clears approval and returns to the delivery checkpoint, without publishing the changed work or resetting the refresh count. Missing/outdated/unverified requested proof prevents automatic shipping. Releases with requests always need the coordinator's explicit decision explaining that earlier proof cannot cover the release version; the sole version exception is Petrina's own exact, verified version-number commit. Any other change requires a new decision. Confirmed deliveries and interrupted publishing evidence remain owned by their products.

Testers and reviewers see whether saved results still match the code and all required commands and hooks, using the same freshness rule as the gates. Current complete passes can satisfy automated acceptance without another full run; user acceptance still needs to be tried. Changed or uncommitted code, changed checks, incomplete runs and uncertain hook inputs never become a current pass by being shown to an agent. A read-only review does not invalidate a run on unchanged work.

Before a fresh Tester, each repository is brought up to date before preparing its checks. A saved Tester or Check finder first finishes the version it was already examining. Completing check discovery restores the normal source update before acceptance commands; only a saved Tester still finishing its version defers that update.

Each check operation shares one observation of its commit, tree, tracked changes and hook definition. When a check run waited in the shared line, including through a pool pause, admission repeats the source update its guarded step normally performs, once, before reading those inputs again or starting commands. Review also repeats the tamper check and settles Petrina's own findings on the updated work; final delivery checks the approved change again. Acceptance retains the saved-conversation exception above, and a release's version commit is checked as prepared. A conflict takes the ordinary Builder port, or a changed approved change returns to the delivery check, before any command starts: the attempt stays recorded as not run with its reason and releases its place. No second fetch is added when the run did not wait.

Changed discovery inputs give up the check place before the Check finder works again; the run then rejoins at its original order. Review-context capture remains a fresh boundary; a saved current flag alone proves nothing. Settled native failures remain in history without repeating their old diagnostics to reviewers; open failures and agent finding history remain visible. A newer main commit alone never clears a failure or makes earlier evidence current: reuse still requires the same complete tree and check definitions.

A passing check operation revalidates its inputs before handing control onward. If required commands, hook inputs or the code changed while it ran, the old result stays historical and current requirements run again. Repeated changes stop verification explicitly rather than permitting acceptance or publishing on an obsolete pass.

A Tester must report each item in a saved acceptance checklist; missing items are repaired in the same conversation. A failed acceptance run never satisfies final acceptance, even if a Builder claims it fixed without changing the patch. Final acceptance failures return to the Builder twice, also while another item could not be verified, then stop at the coordinator's delivery decision; that boundary survives a restart. A new change request authorizes another bounded attempt.

In a shared task a reproduced acceptance failure returns only its affected products that still have acceptance returns ([shared work](repositories.md)). Where the repair goes back to depends on which testing found the failure, saved with the repair so a retry or restart keeps it; a repair saved without that record counts as an early one. A repair of acceptance testing that ran before the delivery check returns to ordinary acceptance testing, described as checking the repair, and then continues through the rest of the plan in order: every review still owed runs, under its usual rules, before any delivery decision or publication, and completed stages the repair did not affect are not repeated. Only acceptance testing the delivery check started, and repairs of what it found, return straight to that check without another review round. A delivery check Petrina added never skips planned steps that have not run: testing there that would skip them, as in a task saved before repairs recorded their route, counts as checking a repair, whether it passes or its returns are then used up. When the returns are used up with failures still open, the task reuses its delivery check, or adds it once even with delivery approval off, finishes the owed reviews and then asks for an explicit decision. Those held failures never start, join or count toward review fix rounds, review progress, votes or review decisions: reviewers are not asked to confirm or dispute them, no review reopens them or records them in its own result, and a review's completion report keeps them in the task-wide counts while naming them as held for the decision. No automatic repair hands them to a Builder, including one fixing another finding in the same product or continuing its earlier conversation, whose instructions and saved context leave them out; a review repair visits only its own findings' products. Only a passing acceptance run closes them, never a Builder's claim. Review activity grants no acceptance return; asking for changes at the delivery check reopens them for another bounded attempt. The plan, the Next line and progress messages show the repair's test, including once the repair is finished and the test has not started (paused, waiting, while Petrina's own checks run before it, or while a failed check is repaired first), then the owed reviews, and that the decision follows them. A review's saved result neither counts a held failure nor claims a Builder's acceptance fix that a later acceptance run already tested.

### Product checks

The Check finder (an internal role) works out once per product, from its CI first, which commands prove it works; it looks again when the CI or build files change. The coordinator can set them by hand. Petrina runs them itself as argument arrays without a shell, before the first reviewer of every round and again right before the delivery check when the code changed (`packages/engine/src/checks.ts`, `product-checks.ts`).

New command results retain observed startup, exit, both output streams, cancellation and cleanup separately. A pass requires a reported zero exit, complete output and no execution failure, timeout, cancellation or unconfirmed requested cleanup. A failed output reader or an inherited pipe that stays open cannot become a pass merely because the command exited successfully. Diagnostic-file persistence is recorded separately; missing historical execution facts are not reconstructed from prose. Ordinary completion requests no process cleanup and proves nothing about unrelated descendants.

A failing check is an Important finding with the real output, and the work goes straight back to the builder. The builder runs focused tests for changed behavior while working, then hands the change back without rerunning the full product checks or test suite; Petrina runs the configured checks and reviewers read those results. A check only looks: whatever one changes in files git tracks is put back, so no formatter slips unreviewed changes into the work.

Automatic returns are counted per product and per failure episode: at most two Builder turns between a failing result and the next genuine pass, saved across restarts. Only every check and hook passing on the current code and check definitions ends the episode, with no check failure of that product left open, including a saved pass reread on that same code; a new commit that still fails, a check that did not finish, one check fixed while another fails, or a pass on checks or hooks replaced while it ran continues it. Rereading a saved failure after an unchanged return reruns nothing and is no extra attempt; the send-back that follows counts. A Builder answer, including one blaming the environment, leaves the check finding open. Each return walks forward from the Builder through every stage up to the one the checks guarded: a pending review round keeps its number and incremental anchor, a fix made after reviews passed is reviewed again, and acceptance is retried on the final code before the delivery check. Shared repairs started at the delivery check or right before shipping return through the first review after the Builder.

When the episode's returns are used up, the task waits at the guarded step (review, acceptance testing or the delivery check; a failure right before shipping goes back to the delivery check) and raises a check problem: a "your call" delivery item naming each failing check with its short diagnostic, the Builder turns spent and the Builder's last answer, where the task stopped, review fixes no reviewer has confirmed yet, the steps still to come and the next action. Asking for changes gives the Builder one more turn, not a fresh allowance; a still-failing run returns straight to the check problem. The engine refuses approval before removing this item or saving approval fields. An explicit fresh check run preserves the repair allowance and resumes the outstanding workflow only after a pass, including products that normally deliver without asking. Review convergence limits and acceptance returns are separate.

Conventional type checks and lint run first. A static failure skips the remaining commands and hooks, without settling their older failures or treating skipped work as passing evidence. Other commands run serially within the working copy to avoid shared build-output races.

Tasks’ checks use a separate bounded queue (see [Scheduling](engine-runtime.md#scheduling)); full suites and builds compete for the same machine.

### The repository's own commit hooks

Petrina's own git steps never run hooks, so Petrina runs the hooks git would run when committing, as the repository has them (local `.git/hooks`, or `core.hooksPath` for husky, lefthook and the like), alongside the checks: the pre-commit hook with the task's whole change staged on top of where it started (the working copy's HEAD detached at the base for the run, and put back after, even across a restart), and the commit-msg hook on the task's one commit message.

They run like the checks, with no GitHub login, and a failure goes back to the builder with the hook's output, so a hook that keeps internal names out of a public repository works as it does by hand. The builder is told the hooks exist and how to run them itself.

### Findings

Exhausted review rounds stop before final checks or acceptance testing. The coordinator can send a concrete repair request or accept the unresolved review and continue to final verification. Continuing fixes no finding, grants no extra automatic review round and approves no delivery. The pending decision survives pause and restart. Current product checks and required acceptance testing still precede a separate, version-bound delivery approval.

The decision records the open Important findings it covers and the task's own change per product (without main's) when asked; in later review stages, covered findings alone neither send work back nor use rounds up, so such a round passes and says they stay open under the decision. A finding leaves that cover once a reviewer confirms it with a current reproduction or reopens it, acceptance testing fails it again or its products' own change differs from the decided one (unreadable counts as changed); later findings are never covered, and failing checks keep their own route.

The default Code reviewer checks nearby cases affected by the changed code or rule against the starting version on every product, even without a local review guide. A confirmed regression caused by the change is Important even when the intended case now works. Reviewers and Verifiers also judge findings against the approved request, brief and coordinator decisions: an older defect that leaves an explicitly requested repair or concrete acceptance outcome unmet remains Important/real, with the governing requirement and current reproduction explained. Age alone does not exempt it. A confirmed older bug unrelated to the task is Pre-existing, a follow-up that never blocks. Nearby code, a general wish for quality and speculation add no scope; an unclear requirement needs investigation. Missing or unavailable proof stays separate from reproduced code defects under the acceptance proof-request rules. These shared classification rules reach built-in, edited and added roles by their findings or votes result, without rewriting saved custom wording or historical judgments.

Reviewers tag each finding Important, Nit or Pre-existing, report a whole class of bug once, and confirm or dispute an earlier report by its id. New reports keep separate ids: wording never establishes identity or cross-tool agreement. The Builder can resolve several reports with one fix, answering every id. Finding counts therefore count reports, not distinct underlying bugs. From round two reviewers inspect only what changed since the last round, and after round three the builder is asked to step back and reconsider.

### Reopening a settled finding

Confirming a dismissed finding or one the Builder claimed to fix reopens that same finding only with its explicit id and a current reproduction; a current reproduction on changed code likewise reopens a finding a vote left unresolved, whose next ballot uses fresh answers, while a confirmation on the code it was left unresolved on keeps that ballot (trees decide where both reviews recorded one, otherwise commits); an old id alone asks that reviewer to correct its result in the same conversation, before any finding changes. This applies to code, security and added reviewers. A separately worded new report never silently reopens a historical finding. The current reproduction reaches the next Builder and voters, while the earlier evidence, votes, confirmations and disputes stay in history.

The reopened finding needs fresh support on the changed code; its original raiser is not assumed to endorse it again. Older saved reopened findings with pre-fix verification are checked again too. A prior dismissal stays settled without new current proof; a fresh reproduction keeps the earlier verdict as history and receives a new check without counting the original raiser as current support. Native check findings follow the actual check results.

Reproduction evidence accompanies open findings to Builders and voters.

### Independent review and voting

Every reviewer in a round looks at the change at the same time, blind to what the others find. An explicit confirmation of a supplied finding id from another tool backs it; ids absent from the saved input are refused. Separate blind reports never create agreement from equal or similar prose. An Important finding no second tool has backed goes to a vote by fresh Verifiers, who each say real, not a bug, a nit or pre-existing. Verifiers prefer high-effort profiles for these specific claims; discovery reviewers keep their configured effort. Every vote and its reason remain with the finding.

The vote uses a bounded panel (`packages/core/src/verifier-panel.ts`), not one Verifier per registered tool. Before anyone starts, the engine resolves each ready tool's verifier choice with its usage, model and capacity stand-ins, keeps one per actual tool, and saves that usable set with the panel. A tool already out of usage or not ready at that moment is left out rather than reserved as a future tie-breaker; a full pool or tool slot, or usage near a limit, keeps a tool eligible and its place waits. With no usable tool nothing is saved and the review waits as before. The panel is one shared initial pair on distinct actual tools, or one Verifier when only one tool is usable, preferring tools with the fewest overlaps with the findings' authors (for a reopened finding, the reviewer whose current reproduction reopened it), then the tools' stable order. Mixed authors share the pair. Different profiles on one tool are one source.

Settlement, once both initial places finished their assignment: any real answer keeps the finding Important; a real/not-blocking split is recorded as a disputed Important decision with both reasons. When both answers say it does not block, whether with the same or different verdicts, that contradicts the original Important report: if the saved usable set had a third tool, only those finding ids get a third answer, in a new journey step with fresh conversations and the original evidence, never a peer's ballot. Compatible ids share one place; places split only when per-finding independence requires it. Any ready tool that has not answered a finding may give it, including one replaced before answering it or one that answered only other findings, preferring tools usable now and away from the authors. A tool left out of the saved usable set may give it only when it can start now; the place waits only for a tool that was usable at selection. After a third answer, or on a panel whose usable set had only one or two tools, the most common other verdict settles it (nit, then pre-existing, then not a bug on a tie). No fourth answer is asked. A finding whose required third answer no ready tool can give stays Important and unresolved, without a verification, and its completed ballot is not repeated on the same code in later rounds or stages, even when a reviewer confirms it again; a current reproduction on changed code reopens it for a fresh ballot. Three sampled tools can still downgrade a report an unasked fourth would keep: this saves starts, it does not promise a full panel's classification.

Every place must finish its assignment before settlement; an absent, invalid or unverified answer never counts as agreement, and a mathematical outcome does not cancel running Verifiers. Each answer records its stage, round, reviewed versions and place, and counts only on that ballot; older rounds' answers stay history. Partial answers are saved at once; corrections keep both reasons and the latest counts. A place records only answers it still owes or its own tool's corrections: an unasked answer from a replacement, or a second answer from a tool that already answered the finding through another place, changes nothing. Rounds saved before bounded panels keep their admitted voters and majority rule (at least half real) until they finish. Where no panel was saved, answers proven for the same stage, round, reviewed versions and episode keep their tools' places and only the missing answers are asked; unproven answers stay history.

Before any reviewer starts, the engine saves the round's brief, Builder reports, check evidence, earlier findings and follow-up cards as one immutable snapshot. Queued reviewers and interrupted rounds read that same snapshot after a restart; a faster peer's current-round report never enters their input or result-validation baseline. Coordinator messages remain live and reach each intended participant.

After every reviewer reports, the reviewers' step saves the findings as settled for that round, including unsupported dismissals, shared fixes, proven repairs of pre-existing bugs and unmentioned Builder fix claims. This copy is marked settled before the step closes or hands findings to voters. The vote step saves its own settled copy after tallying only the reports it checked. Each participant's original hand-back and finding copies remain unchanged. Closed steps are never refreshed from later rounds or current findings; older unmarked copies remain hand-back evidence, not settled decisions.

The reviewers' copy covers reports touched or decided in that round and fix claims not yet examined by a completed review. It collects accepted hand-backs across Try again steps of the same stage, round and saved review input, stopping at an earlier completed examination. It records which reports were raised, fixed, reopened or dismissed and which Builder claims the round examined. Reopenings are recorded as each accepted report is applied, so a later step's start cannot hide them. When an unfinished older review resumes, its saved participant copies supply earlier reopenings before a new hand-back records transitions explicitly. Earlier unchanged decisions and unmentioned reports are not counted again; an older report explicitly confirmed for the first time remains an earlier report. The settled marker proves that every reviewer reported, including when Try again finishes the same round in another step. Once that step closes, summaries, saved copies, the round view and later claim handling use that same round history and proof of completion; the earlier partial step remains incomplete. In memory, the round keeps its opening baseline across retries. After a restart, the observed baseline remains labelled engine-start; recorded round transitions and finding copies retain their original attribution.

Verifier explanations display the recorded outcome separately from counts of each verdict: must be fixed in this change, a real problem already there before the change, a real but minor problem, or not a bug. Counts use the latest vote per recorded actual tool, never nominal profiles or missing tool identities. Pending and unresolved votes also show those counts and explain why the finding remains Important; an unavailable required answer retains its saved explanation. Split votes also say how many tools affirm that the problem exists; pre-existing and minor verdicts affirm existence. Presentation never recalculates the outcome or changes the voting policy.

A selected voter's usage or capacity wait never removes its required place or lets a completed partner cover it, even after the partner finishes. A usage replacement may take a place only on a currently usable tool independent of every finding the place still owes and never on a tool still working another unfinished place of the same step. Each place is named on its own, so a tool that finished another place may take this one with its own seat, conversation and working copy; it answers only those findings, the reason is saved with the new start, and accepted partial votes keep their attribution. Otherwise the missing voter waits visibly. Selected profiles stay protected from removal while the task is unfinished. The timeline and each Verifier's journey input name the tools usable at selection, the chosen places, author avoidance, replacements and third answers; the coordinator's drain status lists every place, what it still owes and the third-answer decisions.

The same preparation saves each product's base-version review guide and commit-specific full, incremental and port comparisons in private files. Fix-round Code reviewers read a separate incremental file rather than rereading the original patch. Lockfile changes remain listed in the statistics and have separate patch files; they remain in review scope, including dependency and integrity checks. Security reviewers and Verifiers retain full-change scope. Reviewers receive file references rather than repeating Git discovery. Raw diffs stay out of task/window state. The in-memory input is reused without disk reads; after a restart its files are verified when loaded. Detached copies use the snapshot's exact commits.

### Reviewer working copies

Each reviewer and voter works in a copy of the change of its own (a detached worktree of the task's commit, with nothing installed, deleted when it finishes), so a test one runs or a checkout one makes never disturbs another or the task's copy. The copy's folder, in every product, is named by a reversible encoding of its member name (`packages/repositories/src/copy-name.ts` `copyFolderName`): place names stay the logical identities, while folders hold only lowercase letters, digits, dashes and escapes, so a third answer's `third:` place and names differing only in case or punctuation get distinct folders on every system. A member never shares a folder already held in its group, such as a copy a screen wait kept under an earlier version's naming: it takes the next free `.1`, `.2`… folder, a form no encoded name has. A member back from a full model returns to the copies it made, and one resumed from a screen wait reopens the copies its saved turn kept. Each holds a slot of its own and starts when the pool and its tool allow, so a small pool takes turns; what each hands back is saved as it arrives, so a restart only redoes the rest.

A stage with a single reviewer runs it as one ordinary step, which can pick up its conversation after a restart or be taken over. In a fix round the builder answers every finding by id. Summaries start with a count, or say "Nothing to fix".

### Risk

The planner rates every task Low, Medium or High from what it touches; unrated work counts as Medium. High-risk work gets a Security review on a tool other than the builder's. Where a product opts in, low-risk work with passing checks and nothing Important open ships without the delivery check. An approval covers the change itself (git's patch-id), on top of whatever main is when it ships: main moving on underneath keeps it, but if the change reads differently on top of the latest main, or the work changed, the coordinator is asked again.

### Review guide

`REVIEW.md` at the repository root, reached the way every agent reaches project knowledge: `AGENTS.md`, which Claude Code and Codex load by themselves, has a short "Review guide" section pointing to it, so an agent Petrina starts and one the coordinator starts read the same guide. Petrina's reviewers are told to judge by the guide as the base branch has it: whatever the change itself writes into `REVIEW.md` or `AGENTS.md` is part of what they review, never a rule, since a change cannot set the rules it is judged by.

When the coordinator sends back a delivery every reviewer passed, the Guide keeper proposes one point; accepted, that task's reviewers get it with the task, like the coordinator's notes, and it is committed to `REVIEW.md` on the branch that ships (the first one also adds the section to `AGENTS.md`).

Review-guide points retain the exact commit that incorporated them: they are no longer written into deliveries, but still accompany reviews pinned before that commit. A later base that already incorporated a rule respects subsequent edits or removal instead of restoring the old instruction. Instructions only on an unpublished branch stay pending; an unreadable repository proves nothing.

The Analytics page shows how reviews are going: rounds to pass, what became of each finding, deliveries sent back, and how each reviewer profile's Important findings held up (`packages/core/src/reviews.ts`).
