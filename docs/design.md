# Petrina design

How Petrina works inside. The user-facing side is in [ux.md](ux.md).

## Goals

- Run a squad of local coding agents on a product's GitHub repository, many tasks at once, with roles as first-class objects.
- Never show code in the app. Every stage hands back plain-language results.
- Make adding a tool, a model or a role cheap: usually configuration, rarely code.
- Run entirely on the user's machine with the tools they are already logged into. No API keys, no Petrina server, no telemetry.
- Never merge a pull request.

## What Petrina does better than the tools around it

Competitive research (October 2026) found the building blocks in other tools, but nobody combines them:

1. **A planner composes each task's plan from roles,** choosing tool, model and effort per stage, shown as an editable plan before anything runs.
2. **Roles are separate from tools:** instructions, permissions, what they see, and what they must hand back.
3. **Design convergence:** two architects on different tools iterate until no blocking objection is open, with a disagreement log and a round limit.
4. **Reviews that converge:** reviewers on different tools looking at the change at once, each on its own (never seeing the builder's transcript); Petrina's own checks as evidence; fresh agents voting on Important findings before they send work back; and review depth and the delivery check set by the task's risk.
5. **A light, live board** instead of an IDE.

Mechanics borrowed and credited:

- A stage finishes on a structured result, never on a model saying it is done (bmad-loop).
- Stage kinds with loops, caps and approval gates (Archon).
- Reviewers in fresh sessions, told to prove "done" wrong; pass/fail findings with file:line, never scores; a mechanical tamper check for deleted or skipped tests (no_human).
- One generic agent protocol for many tools (Kandev).
- From "Solving code review at Anthropic": checks the agent cannot talk its way past, findings tagged Important, Nit or Pre-existing, a finding verified before it counts, every finding answered, convergence rules (no repeats, whole classes of bug, diff-only re-review, a step back after three rounds), approval by risk set from the change, an approval that covers one commit, a per-repository REVIEW.md that learns from misses, and measuring rounds to pass.

## Concepts

| Concept | What it is |
|---|---|
| **Product** | A GitHub repository and its local clone |
| **Task** | What the coordinator wants. Has a priority (its place in the queue) |
| **Role** | Data: name, purpose, permissions, what it sees, and whether only Petrina runs it (internal: the planner never hears of it) |
| **Role contract** | What a role is told, which parts of the context it reads, and the result it must hand back (`packages/engine/src/roles.ts`) |
| **Agent profile** | Tool × model × effort, for example Claude Code · Opus 5.5 · high |
| **Tool** | Something that can run an agent. Usually an ACP command line |
| **Plan** | Ordered stages. Each stage: kind, role, profiles, round limit, checkpoint |
| **Stage run** | One execution of a stage: rounds, agent sessions, events, result |
| **Inbox item** | Anything waiting on the coordinator |
| **Product checks** | The commands that prove a product works (type check, lint, tests, build), run by Petrina itself |
| **Review guide** | `REVIEW.md` in the repository, which `AGENTS.md` points every agent to; it grows with points the coordinator accepted after a miss |
| **Risk** | Low, Medium or High, rated by the planner from what the task touches |

### Stage kinds

| Kind | Behaviour |
|---|---|
| `do` | One role on one profile produces its result |
| `converge` | Author and reviewer (different profiles) alternate until the reviewer has no open blocking objection, or the round limit is reached and the coordinator decides |
| `review-chain` | Petrina's tamper check and the product's checks first, then every reviewer at once, each on its own, then fresh agents voting on Important findings. Important findings that stand send the change back to the builder as one list, then the review runs again on what changed: within the planned rounds, and past them while each round leaves fewer Important findings than the one before, up to five. A round that stops making progress goes to the coordinator, whose delivery check then says "your call" with the count still open |
| `do` with the Tester | Tries the acceptance list like a user, once on the change before its first review. Fix rounds skip it (the code reviewers check the fixes), and right before the delivery check the tester tries the final code once more if it changed since; a failure there goes back to the builder like a failing check |
| `gate` | Waits for the coordinator (design approval, delivery approval) |

### Task lifecycle

```
queued → planning → designing → building → reviewing → ready → done
            │            │            │           │        │
            └──── any stage can be: running · needs-you · paused · failed
```

The stage column (planning, designing, building…) is derived from the role of the current stage; the Products page counts tasks by it. The board itself is one grid of cards grouped by what each task needs (needs you, working, waiting, queue, done), and every card shows its own pipeline from its plan: done steps checked, the current one named, stages the plan does not have left out (`packages/core/src/board.ts`).

## Roles

Roles are records the engine saves and keeps across restarts (`packages/core/src/roles.ts`). The engine and the demo squad share the rules, and the engine enforces them, not the Library's form.

- **Built-in roles** keep their name, icon and kind of result, because Petrina depends on them. The coordinator can change their purpose, how they work and what they hand back, and their permission unless that would break how the squad works: the Planner is always read-only, reviewers never change the work they judge, and the Builder always makes changes. Only the fields the coordinator changed are saved, so the others keep following Petrina's defaults; **Reset to default** drops them. The Release Manager is shown but can't be changed: it writes release notes while Petrina handles delivery itself.
- **Added roles** (at most 20) hand back notes or pass-or-fail findings, chosen once. A notes role works in a `do` step, and what it hands back reaches every later agent on the task. A findings role joins the review next to the code reviewers: it sees the design, the acceptance checklist, the builder's report and earlier findings, confirms or disputes them (every dispute gives its reason, as for the code reviewers), and its blocking findings go back to the builder under its name. A removed role leaves the Library and the planner's list, and stays known to the tasks that use it.
- **Refused, whoever sends it:** an unknown role, any change to the Release Manager, a locked permission, a changed kind of result, a changed name, icon or colour on a built-in role, a duplicate name (ignoring capitals, counting built-in names), a missing name or purpose, text over the limit (name 40, purpose 200, instructions 4,000, hands-back 300 characters) and a 21st added role.
- **What an agent is told:** its role's wording, inside Petrina's fixed rules for its kind of result (never its name, so an added role gets the rules of the built-in role it works like), then its purpose, one sentence on what it may change in this step and what it hands back, with the task, the coordinator's notes and the result format as before. The planner's fixed rules (the roles and profiles it may use with what each one does, the stage kinds and the rules) come after its wording and can't be replaced by it. The Release Manager is told exactly what it was before.
- **Every step that may change the product comes before the final review** (the plan's last review chain). The engine moves one the planner put after it, and the plan's reason says so; a step that still ends up after it, because its role was switched to changing the product after planning, runs read-only and the timeline says why. Read-only steps may still run after the final review. No planned role changes the product after the final review. Petrina adds delivery last, after the final review and the delivery check, as before, and handles publishing itself; only the read-only Release Manager works there, and only for releases.
- **Misplaced roles are corrected, never stuck:** findings in a `do` step join the final review, notes or checks in the review get a step of their own before it (also when the plan names a role for every reviewer), any other role there that doesn't review is replaced by a code reviewer or left out, an added role in the design pair gives way to the built-in one, internal roles, including the Release Manager, are left out wherever the planner put them, a role removed while the planner planned is left out, and the final review always keeps a code reviewer. The plan's reason says what Petrina changed.
- **Work is never lost between roles:** a role that may change the product has its work committed at the end of its step, labelled with its name, so a later read-only role never wipes it. Read-only roles, added ones included, have their changes and commits undone when their step ends.
- Changes reach the next agent that starts and the next plan. An agent already working finishes with the version of its role it started with, its wording, name and permission included, even when Petrina restarts in between and its conversation starts again. Reviewers and voters working side by side each keep their own saved version; a replacement on another tool keeps it until that part of the review finishes.

## Tools: ACP first

Petrina talks to agents through the [Agent Client Protocol](https://agentclientprotocol.com) (ACP). Claude Code and Codex have maintained ACP adapters. Grok is the ACP server itself:

| Tool | ACP adapter |
|---|---|
| Claude Code | `agentclientprotocol/claude-agent-acp` (Claude Agent SDK) |
| Codex | `agentclientprotocol/codex-acp` (Codex App Server) |
| Grok | `grok --permission-mode auto agent stdio` (no Node adapter; model `grok-4.7`, effort `reasoning_effort`) |
| Others | Any agent that speaks ACP: Gemini CLI, OpenCode, and more as they add it |

ACP gives Petrina what it needs without per-tool code:

| Need | ACP |
|---|---|
| Start a session in a working copy | `session/new` with `cwd` and the MCP servers to attach |
| Send a message | `session/prompt` (one turn at a time, which is what makes queued messages natural) |
| Interrupt | `session/cancel` |
| Live activity for the status line | `session/update` notifications (messages, tool calls, plans) |
| Permission prompts | `session/request_permission`, sent only when the tool's own safety check flags something; the coordinator answers |
| Pick up after a restart | `session/resume`, or `session/load` (which replays the conversation) when that is all the agent offers |

So a tool is mostly configuration:

```json
{
  "id": "codex",
  "name": "Codex",
  "command": ["npx", "-y", "@agentclientprotocol/codex-acp"],
  "models": ["…"],
  "efforts": ["low", "medium", "high", "xhigh"]
}
```

A dedicated adapter is written only when a tool needs something ACP does not expose (for example reading usage limits). Codex's usage (`packages/engine/src/codex-usage.ts`) is one request to its app-server. Grok's account usage (`packages/engine/src/grok-usage.ts`) is an ACP initialization and its read-only billing extension, without opening a session or sending a prompt. Only the allowance percentage, period and reset time are retained. Both scheduling and Analytics share each tool's reader. Things to verify per tool before relying on them: model and effort selection through ACP, use of the user's existing login, and `session/resume` or `session/load` support.

### Checking the tools

The engine checks Claude Code, Codex, Grok, the GitHub CLI, Git and Node.js when it starts, during first run, from the Library, and before a step or a delivery needs them. Each check has a time limit (8 seconds) and runs outside any product's folder; a slow one never holds the others. Programs are looked up the way the Library finds the agent tools, on the PATH as it is now, so an app opened from the Dock finds what Terminal finds. A tool that doesn't answer in time is Couldn't check at once and is stopped, forced after 2 seconds if it ignores being asked; the next check of that tool waits until it is gone, so Check again never piles up copies. A login check opens a conversation the way an agent's starts (same command, same environment, in an empty folder of Petrina's own) and closes it before any message, so it costs nothing. Ready takes the tool's own word, given the way that tool gives it (`login` on its adapter). Claude Code and Codex open a conversation while logged out (Claude Code asks for a login only at the first message), so for them Ready is the login their connector reports over ACP (`_auth/status_update`), where "none" means Not logged in. Grok sends no such report: it signs in as the conversation opens and refuses with ACP's "log in first" error when it can't, so for Grok a conversation that opens is Ready. ACP's "log in first" error means Not logged in for every tool, and a tool that says nothing within the time limit, or anything unclear, means Couldn't check. A program that isn't on the PATH is Not installed at once, with no Checking in between. On a Mac, Git is checked without running Apple's stand-in that opens the developer-tools installer.

The agent tools are Claude Code, Codex and, when it is installed, Grok. The squad uses the ones that are Ready, or if none is, those Petrina couldn't check, never one that is Not installed or Not logged in; a usage stand-in comes from the same tools. The planner is only offered profiles on those tools, and every step of its plan, the Release Manager, the Check finder, the Guide keeper and the review's voters move to the same kind of profile on a usable tool. With both tools Ready nothing changes. A step whose tool is not ready, won't start (or doesn't open a conversation within two minutes) or asks for a login becomes a Stuck item naming the tool, with its fix; Retry checks the tool again before trying. A pull request or release checks the GitHub CLI's login before the delivery gets ready, so nothing goes out halfway; commit to main needs no GitHub.

### Needs a real device: first run

These do not block shipping. The flow, its screens (light and dark, keyboard only) and the engine's checks are covered by tests and a headless browser; these need the installed app or another system:

1. **Installed desktop app, and the first minute.** Install Petrina on a Mac where Claude Code, Codex and the GitHub CLI are installed and logged in, with a GitHub clone in `~/code`. Open it from the Dock for the first time: "Starting Petrina…", then Welcome, and every tool Ready (found through the login shell's PATH). From opening Petrina to the planner running takes under 60 seconds. Then the same with GitHub not answering: the first card still plans, within about 30 seconds of the usual time, from the copy on the machine, and its timeline says so.
2. **Mac permission windows.** On a Mac, first run never brings up the system's "would like to access your Documents folder" window (or Desktop or Downloads) while it looks for clones. On a Mac without Apple's developer tools, the Git row says Not installed and the developer-tools installer never opens by itself. A guide link opens in the default browser, outside Petrina.
3. **Windows.** First run on a Windows PC: fixes show the Windows commands (winget) and say "a terminal", clones in `source\repos` are found, a pasted path with backslashes or `~` works, and a guide link opens in the default browser.
4. **Linux.** First run on a Linux desktop: fixes show the Linux commands, and a guide link opens in the default browser.

## Results and questions

An agent hands back its result as one fenced `petrina` block of JSON at the end of its last message, in the shape its role contract shows it. A stage finishes only when that block parses and passes the role's schema; otherwise the agent is told exactly what is wrong, twice at most. An agent that cannot go on without a decision ends with a `needsInput` block instead: the question goes to the inbox, and the answer comes back to the same conversation. The status line comes from the agent's own plan and tool activity over ACP. Agents get no extra MCP servers.

## Permissions

Petrina relies on each tool's own safety checker instead of building one:

| Tool | Mode | Who decides |
|---|---|---|
| Claude Code | Auto | Claude Code's classifier allows or blocks each action |
| Codex | Auto review | Codex's reviewer approves, inside Codex's own workspace sandbox |
| Grok | Auto | Grok's own checker. The process starts with `--permission-mode auto`, and the session asks for auto mode (`autoMode` on `session/new`, `session/resume` and `session/load`). A saved always-approve setting would otherwise win. Never an always-approve or yolo flag |

- Petrina reads no commands. When a tool's checker flags something and asks, the question goes to the inbox unchanged, with the exact command or paths, and the coordinator allows or denies it once.
- Petrina never picks a tool's "always" option: those write settings into the working copy or switch modes.
- Nothing is remembered: every request is allowed or denied once, in the inbox or the session, with the same wording and buttons in both. There are no remembered rules per product or permission controls in product settings.
- If a tool's automatic mode is not available for a model, the session log says so and that tool asks before acting.
- Approval gates and round limits are enforced by the engine, never by prompting a model to stop.

## Messages to a running agent

- Messages queue per task. When the agent's current turn ends, the next queued message is sent with `session/prompt`.
- Interrupt sends `session/cancel`, then the message.
- Every delivered message and reply is written to the session transcript the Session tab shows.

## Checks, reviews and risk

- **Product checks.** The Check finder (an internal role) works out once per product, from its CI first, which commands prove it works; it looks again when the CI or build files change. The coordinator can set them by hand. Petrina runs them itself, side by side, as argument arrays without a shell, before the first reviewer of every round and again right before the delivery check when the code changed (`packages/engine/src/checks.ts`, `product-checks.ts`). A failing check is an Important finding with the real output, and the work goes straight back to the builder. The builder is told to run every check in full before it hands back; reviewers read Petrina's results instead of running the suite again. A check only looks: whatever one changes in files git tracks is put back, so no formatter slips unreviewed changes into the work. Tasks' checks take turns on the machine (one run per six cores at a time, at least one): several full test suites and builds at once, with a security scanner inspecting every process they start, are slower for each and time out for nothing.
- **The repository's own commit hooks.** Petrina's own git steps never run hooks, so Petrina runs the hooks git would run when committing, as the repository has them (local `.git/hooks`, or `core.hooksPath` for husky, lefthook and the like), alongside the checks: the pre-commit hook with the task's whole change staged on top of where it started (the working copy's HEAD detached at the base for the run, and put back after, even across a restart), and the commit-msg hook on the task's one commit message. They run like the checks, with no GitHub login, and a failure goes back to the builder with the hook's output, so a hook that keeps internal names out of a public repository works as it does by hand. The builder is told the hooks exist and how to run them itself.
- **Findings.** Reviewers tag each finding Important, Nit or Pre-existing (a follow-up that never blocks), report a whole class of bug once, and never repeat a finding; Petrina drops repeats itself. From round two they review only what changed since the last round, and after round three the builder is asked to step back and reconsider. Every reviewer in a round looks at the change at the same time, blind to what the others find; the same finding from a reviewer on another tool backs it. An Important finding no second tool has backed goes to a vote: one fresh agent per tool (the Verifier) says real, not a bug, a nit or pre-existing, all at once. It stands when at least half the voters say it is real; otherwise the most common other verdict settles it. Each reviewer and voter works in a copy of the change of its own (a detached worktree of the task's commit, with nothing installed, deleted when it finishes), so a test one runs or a checkout one makes never disturbs another or the task's copy. Each holds a slot of its own and starts when the pool and its tool allow, so a small pool takes turns; what each hands back is saved as it arrives, so a restart only redoes the rest. A stage with a single reviewer runs it as one ordinary step, which can pick up its conversation after a restart or be taken over. In a fix round the builder answers every finding by id. Summaries start with a count, or say "Nothing to fix".
- **Risk.** The planner rates every task Low, Medium or High from what it touches; unrated work counts as Medium. High-risk work gets a Security review on a tool other than the builder's. Where a product opts in, low-risk work with passing checks and nothing Important open ships without the delivery check. An approval covers the change itself (git's patch-id), on top of whatever main is when it ships: main moving on underneath keeps it, but if the change reads differently on top of the latest main, or the work changed, the coordinator is asked again.
- **Review guide.** `REVIEW.md` at the repository root, reached the way every agent reaches project knowledge: `AGENTS.md`, which Claude Code and Codex load by themselves, has a short "Review guide" section pointing to it, so an agent Petrina starts and one the coordinator starts read the same guide. Petrina's reviewers are told to judge by the guide as the base branch has it: whatever the change itself writes into `REVIEW.md` or `AGENTS.md` is part of what they review, never a rule, since a change cannot set the rules it is judged by. When the coordinator sends back a delivery every reviewer passed, the Guide keeper proposes one point; accepted, that task's reviewers get it with the task, like the coordinator's notes, and it is committed to `REVIEW.md` on the branch that ships (the first one also adds the section to `AGENTS.md`).
- **Measuring.** The Agents page shows how reviews are going: rounds to pass, what became of each finding, deliveries sent back, and how each reviewer profile's Important findings held up (`packages/core/src/reviews.ts`).

## Scheduling

- The queue is an ordered list. Priority is position.
- A pool limit caps running agents, with optional caps per tool. A tool past 80% of a usage window gets half its cap of new agents (see Balancing under Usage limits).
- Taking a slot records the next agent and its profile (and therefore its tool) at the same moment, before working-copy setup or agent I/O. The card shows the correct step immediately; a new task shows Plan with its planner.
- Before every new agent, including the same tool, a new design/review round or a new stage, check the pool and tool limits again, excluding this task's old slot. Keep the slot if there is room; otherwise release it and wait at the current step, keeping the working copy and progress. The status names the busy tool, a full pool, or a paused pool.
- A step where several agents work at once (a review round's reviewers, its voters) holds a slot for each of them: the first takes the task's own slot, and each other one starts only when a slot of its own is free under the pool limit and its tool's cap. One that cannot get a slot waits for the next round of scheduling, like any other agent.
- A task waiting at a gate releases its slot. An agent waiting on a mid-stage question keeps it and is shown as waiting on the coordinator.
- When a slot frees, work already in progress continues first (when the pool cannot take all of it, the tool with more of its limit left goes first), then the first queued task that is not held and whose next tool is under its cap.
- Lowering a limit never stops a running agent. Each finishes, and its successor waits if the other tasks still fill the new limit. Pausing the pool also holds tasks between agents.

The scheduler is a pure function in `@petrina/core` (`pickStarts`), tested without any I/O.

### Usage limits

- Claude Code reports its usage on every turn (how much of each limit is used, and when it resets). The session window is `status` and the spend cap is `overageStatus`, the same three values (`allowed`, `allowed_warning`, `rejected`). A failed turn with no report carries a code instead: Claude's `errorKind` (`billing_error`, `rate_limit`, `account_on_hold`), Codex's `codexErrorInfo` (`usageLimitExceeded`, `rateLimitExceeded`), or Grok's `error: "rate_limit"`. Only when Claude sends no code, because the block was a synthetic message, Petrina matches that message against Claude's own prefix list. Grok's one known sentence ("You've hit the rate limit for your plan.") is matched the same way, on the error text only. A busy service or a server error is not a usage limit. The pool keeps the latest report per tool and kind of limit (`pool.usage`) and who is out until when (`pool.limited`). The window shows both in plain words next to the pool. Limits whose time has passed are dropped every time the scheduler runs, and a timer runs it again at the first one's end. A window it reports as rejected while the account goes on with extra usage (`isUsingOverage`) is spent, not out: the agents keep working, the usage line says "used up, on extra usage", fewer new agents start on the tool and the balancer prefers tools with room. A rejected window without extra usage takes the tool out until it resets, before any turn fails on it; Codex's own count works the same way.
- Codex says nothing about its usage over ACP: its adapter reads the limits from Codex's app-server for its own status line and keeps them. Petrina reads them itself (`packages/engine/src/codex-usage.ts`): it runs `codex app-server` as an argument array with the agents' environment, does the adapter's `initialize` handshake, asks `account/rateLimits/read` once and stops the process. Each named limit and window becomes a report, with its duration and reset time: 100% used is `rejected`, from 90% a warning. It reads when the engine starts (Codex installed), whenever a Codex agent starts, every ten minutes while any agent runs, and when Analytics or a finished turn asks for a fresh reading (at most once per minute or five minutes respectively). These requests share one reader and feed both the scheduler and the history; a failure (not installed, not logged in, no answer within 20 seconds) goes to the engine log once and never fails a task. A report that says a tool is out marks it out until the reset even when no turn failed on it. Grok reports its account allowance through the read-only `_x.ai/billing` ACP extension. Petrina initializes the installed CLI, asks once and stops it, without a session or prompt. Its percentage and weekly or monthly reset feed the same scheduler and history. Reads at startup, before work, after turns and from Analytics share one reader, with the same one-minute page and five-minute background gaps.
- A limit is for the whole tool, except Claude Code's weekly Opus and Sonnet limits, which are for that model only.
- One function (`chooseProfile` in `@petrina/core`, used through `Kernel.choose`) decides who really works a step: the planned profile when it is free, else another model on the same tool, else a profile on another tool (the same effort first, in the order of the profile list, never one the coordinator removed). It is used wherever an agent is chosen, so the slots count the right tool. With nobody left, the task waits without a slot ("Waiting for usage: …") and starts by itself when a limit ends. The plan is never rewritten: once the limit is over, later steps use the planned profile again. A usage stand-in whose tool is already at its cap yields to the next tool that has a seat (`chooseWithRoom`). The profile the plan named still waits for its own tool: the cap is there so one tool cannot take every seat.
- When a turn ends because its tool ran out, the step starts again right away on the stand-in, in a fresh conversation told what the first agent did (the same summary a restart gives), what it last said and that its unfinished work is in the working copy. With no stand-in, the step waits and the first agent's own conversation is reopened when a limit ends. A builder never tries to go back to its own conversation on a tool or model that is out.
- New agents also prefer an equal profile on a tool that is not close to its limit (a warning, or 90% used), when there is one. Running agents are never interrupted for this.
- A usage-limit stand-in for Claude Code's Opus is Sonnet, which the planner is never offered (`standby` in the profile).
- **Balancing.** Reviews from both Claude and Codex are worth having, so the pool keeps their usage level instead of draining one tool first. A tool's room is the unused share of its tightest window per hour until that window resets (`headroom` in `@petrina/core`): 20% left with an hour to go beats 50% left with a week to go. Wherever a choice is open, the tool with more room wins: among stand-ins of the same independence, nearness and effort; among equal profiles when the planned tool is near its limit; and among work in progress waiting for a slot when the pool cannot take all of it. A tool that has said nothing is fine: it is neither held back nor pushed behind one that has. Past 80% of a window (`SLOW_DOWN`) a tool slows down: it gets half its cap of new agents (`SLOW_DOWN_SHARE`, rounded up, at least one; the pool's limit stands in for a tool with no cap), a task waiting for one of its seats says so, and the pool shows "starting fewer agents on it" next to the window and its reset time. Out, it gets none until the reset (`pool.limited`), and planned work continues on the other tool's equivalent profile. Today's rules stand: a reviewer runs on a tool other than the author's wherever both have room, a review with reviewers on both tools never collapses onto one while the other has room, reviewers and voters keep their planned tools when merely near a limit, and the security review stays away from the builder's tool. Running agents are never moved.

## Work log and usage

Petrina records what the squad uses so the coordinator can see what work costs in tokens and time, per task, per product and for the whole squad. No prices: on subscriptions they would mislead.

### What is logged, and where

- **One entry per agent turn** (each message Petrina sends an agent and the reply it waits for), in the `work_turns` table: task and product; the stage, its name at the time (planning counts as a stage), its round, and whether the builder was fixing review findings; role and tool; the profile, model and effort asked for; the model and effort the tool confirmed, or nothing ("not confirmed"); any switch the tool made during the turn; the agent session; why the turn happened (first instructions, a message, an answer, redoing an unusable result, continuing after an interrupt); when it started and ended; how it ended (finished, interrupted, stopped by a pause or cancel, the agent stopped, lost when Petrina stopped); whether it counts the main agent only; the working time; and the tokens: new input, input reused from the cache, input written to the cache, output, reasoning (part of output) and the total. A figure the tool doesn't give is stored as missing ("not reported"), never as zero.
- **One line per model per turn** in `work_tokens`: a model name and token figures, nothing else.
- **One entry per notable moment** in `work_moments`: a stage starting and ending (outcome, start-to-finish time, agent time), each design round (who took part, objections, blocking), how a design ended, each reviewer's pass or fail verdict and the open findings it supported (new or confirmed, each counted once), how a review ended, each question, permission and checkpoint (how long the answer took and what kind of answer), each failure (a plain reason; one Petrina recovers from, like a Check finder or Guide keeper that could not finish, counts too, and each failure counts once however many places see it), each retry (an agent taking over after a usage limit, at once or when the step starts again after waiting for the reset or a free slot; what a step owes is kept in the work log, so a restart keeps it), each result an agent had to redo, and each task delivered, merged, closed or cancelled.
- **Every product Petrina has ever had** in `products_ever`: id, name, repository, when added and, if removed, when.
- **Readings of the tools' usage limits** in `usage_readings`: which limit, how much of it was used, its status, length and reset time, and when the tool said so. The last thirty days are kept, and a reading identical to the latest one of its limit is not written again, so a tool repeating itself on every turn leaves one row per change.

The tables live in the engine's SQLite file next to its state, are kept forever and survive restarts. They hold only numbers, names and ids: no prompts, replies, commands or file paths. The dollar figure Claude Code sends is never read. The app never receives the log: the work-log state only carries a counter that changes when an entry is written and when tracking began. Limits use the existing shared pool reports (`pool.usage`) and blocked tools and models (`pool.limited`), so Analytics, the pool and Agents always read one source. Each view asks the engine for its own numbers with one checked request (`usage`, with a fixed set of views and periods), and asks again when the counter changes or the local day rolls over. The per-product totals are added up by SQLite, so they stay fast after a year of turns. The simulator writes the same entries in memory, and the demos start with thirty days of them.

Questions, permissions and checkpoints are recorded when raised. An answer completes that same entry, retaining when it was asked, even if a pause or restart has removed it from the inbox. Cancelling or pausing never removes the request from history, and unanswered requests never count as zero-length answers. The demos keep inbox requests and their history on the same identifiers too, so answering a seeded request never counts it twice. Design rounds and outcomes name the profiles that actually returned the brief and objections, including replacements, rather than the planned profiles.

Working time leaves out the time an agent waits for the coordinator: permission answers inside a turn are subtracted, and questions, checkpoints and waits for a free slot fall between turns. When an agent asks for two permissions at once, the time either is open counts once, so the overlap is never taken off twice.

### Counting tokens

- Petrina works out every total itself as new input + reused input + written input + output, the same way for every tool, so nothing is counted twice. When a tool gives only a total, that total is used. (Claude Code and Codex already separate cached input; Petrina separates Grok's inclusive input before recording it.)
- **Claude Code** attaches a per-model breakdown to each turn (`_meta.quota.model_usage`, from the SDK's `modelUsage`). It already includes helper agents, side conversations and compaction. Each model is kept as its own line, exactly as reported, and the turn's figures are the breakdown's sum. The main figure (ACP's `usage`, main agent loop only) is never added on top. Without a breakdown, the main figure is kept as one line under the confirmed model and the turn is marked "main agent only".
- **Codex** gives one figure per turn, kept as one line under the model Codex names for the turn. If Codex rerouted to another model during the turn (`model/rerouted`, announced as a notice), the line is marked "changed during the turn": it can't be split between models. A `spawnAgent` tool call means a helper agent Codex doesn't report on, so the turn is marked "main agent only".
- **Grok** reports whole-prompt usage in `_meta.usage`, including collected subagent work. The per-model breakdown is counted once; a valid aggregate without a complete breakdown stays under "Model not reported". Its sibling token fields describe only the last model call and its sibling total is context size. Input includes cache reads and writes, which are subtracted to record new input; reasoning is already included in output. An incomplete report stays unreported. A confirmed resolved model keeps tokens and agent time on the same model row.

### No helper figure, and effort stays on the agent

Claude Code folds helper agents that use the same model into that model's line, so nobody can say how much was helper work; Petrina doesn't try, and keeps no separate helper figure anywhere. Token lines carry only a model and its figures. Effort belongs to the agent's turn (asked for and actually run) and is shown on the agent, never next to tokens. In the model split, tokens group by the model on each line; agent time goes to the model the agent's session ran on; a model that only appeared inside turns shows its time as "not reported". Petrina recognises Claude model ids (family, version, an optional date) and shows them plainly. Grok’s verified `grok-4.7` session alias and `grok-4.7-build` response model share the name "Grok 4.7"; resolving this alias is not a model fallback in profile comparisons. Raw requested and actual ids remain in the log. Every other name, a bracketed ending such as `[1m]` included, stays as reported, so unfamiliar variants never share a line.

### Asked for and actually ran

After setting a profile's model and effort, Petrina reads back the session's config options and records what the tool says it is actually set to. A value the tool doesn't offer isn't forced: the session keeps the tool's default (as before) and the entry keeps both what was asked and what ran. Petrina keeps listening: Claude Code sends a `config_option_update` after a fallback, Codex announces a reroute. If the tool doesn't say, the setting is "not confirmed", never a guess: a tool that acknowledges a change without sending its options back leaves that setting unconfirmed. A switch the tool confirms during a turn is kept on that turn's entry even when the agent stops before replying. Comparisons per profile only count an agent's stage when all its turns, across every round of the stage, ran on that profile's own model and effort. That is judged on the stage's whole history, so a round before the chosen period still takes the credit away. Code and Security reviewers both keep their stages and agent time in comparisons. Profile time follows the same unknown and “at least” rules as every other total.

### Product identities

A product's id is never handed out again. A new product's id is checked against current products, removed products and every id in the work log, so a different repository with the same name, or the same repository added again after removal, starts fresh and never inherits history. Removing a product keeps its entry, marked removed, and its work still counts in squad totals under its old name. On the first start with a work log, any product id a task still points to that is no longer in the list is recorded as removed (without a name: Petrina never kept it). If the saved state is ever lost, task and product ids in the log are still never reused.

### Limits

Claude Code sends limit notices on its context updates (`_meta._claude/rateLimit`): which limit (5-hour, weekly, weekly for one model, extra usage), how much is used when given, a status (fine, close, reached) and the reset time. Codex doesn't send them over ACP, so Petrina starts the installed `codex app-server`, calls `account/rateLimits/read` and stops it: no agent, no thread, no tokens. That happens after a Codex turn (at most every 5 minutes) and when Analytics opens (at most once a minute). Only each limit's percentage, length and reset are kept. A failed read means "not reported". Grok is read through its ACP billing extension with the same gaps, retaining only its allowance percentage, period and reset. These reads update `pool.usage`, alongside Claude Code’s own reports. Limits are stored with the time they were reported, survive restarts, and a passed reset time is shown as such. The same Usage component serves Analytics, the pool and Agents.

The pool keeps only the latest report per tool and kind of limit. Every report from a tool also goes into the thirty-day history beside the work log (`usage_readings`, see above), unless it repeats the latest reading of its limit. Analytics draws from it: for the chosen period, each limit's readings over time with its reset moments (the distinct reset times reports named, once passed) and the next reset when it is known and inside the period, ending each line on the pool's latest report. Analytics also charts tokens over time from the per-model lines: per day (per hour for Today), split by tool, by model or by provider (Anthropic for Claude Code, OpenAI for Codex, xAI for Grok, Google for Gemini: a small map in `@petrina/core`), measuring all tokens, one part of them where the tools reported it, or agent time, with the running total. All three splits are worked out in one view, so the window switches without asking again, and they add up to the same totals. The charts are plain SVG drawn by the app, no library. Missing reports stay distinct from zero; partial buckets and running totals say "at least". Tooltips and tables keep exact token counts while axes stay compact. Limit lines break at known resets and never carry an expired reading across a reset.

### "At least"

A total reads "at least" only when whole turns are known to be missing, judged separately for tokens and time. Tokens: a turn with no token report, a turn lost when Petrina stopped, or work from before tracking began. Time: a lost turn or work from before tracking began. Turns counting the main agent only, cache reuse, the tools counting differently and model changes never make a total "at least"; they are explained once in the "About these numbers" note. Petrina remembers when it started keeping track; tasks that had started before then are marked "earlier work not recorded" for good, and so are their products' totals and any period that starts before tracking began. The splits keep the warning too: in a period that starts before tracking began, every tool, model and role line reads "at least", and so does every product line except products added after tracking began, which can't be missing anything. A turn still running when Petrina stops is marked lost on the next start. When nothing known adds up and work is missing (only earlier work, or only lost turns), there is no number at all: it reads "not known", never "at least 0"; a figure a tool didn't send reads "not reported". Deliveries and cancellations are charted per day in every period, Today as one column.

### Why no prices

Claude Code sends an estimated dollar figure, but on a subscription it describes nothing the coordinator pays, and Codex sends none. Showing it would mislead, so it is never stored or shown. Tokens and time are the honest measure.

## Working copies

- Each task gets a git worktree in Petrina's data folder (not inside the repository), on a branch named `petrina/<task-slug>`.
- Slugs are generated by Petrina from a strict allowlist (`[a-z0-9-]`), never from raw task text.
- Processes are started with argument arrays, never through a shell.
- Petrina gets every delivery ready and publishes it itself (see Delivery). No agent publishes, and Petrina never merges.

## Delivery

- After review, and the delivery check when the task asks for one, Petrina makes sure the work is still what was approved: an approval holds for the approved change (its fingerprint), delivery mode and destination, and anything else asks again. It brings the one commit up to date with the latest default branch (freshly fetched from GitHub for pull requests and releases; if that fetch fails, Petrina publishes nothing and waits for Retry) and runs the checks on it.
- Then Petrina gets the delivery ready itself. A pull request's title is the builder's commit title. Its description is the builder's: the builder writes one for every pull request delivery and keeps it current in fix rounds, and when it has none Petrina writes one from the builder's report, so a missing description never holds a delivery up. Petrina adds its own part under "Checked by Petrina", saying only what it saw: the acceptance checklist (ticked only where a tester checked it), the checks it ran on the commit, who reviewed it (role, tool and model) and the follow-ups older than the change. Text past GitHub's limits is cut. "Commit to main" needs nothing more.
- For a release Petrina works out the version (the latest release plus the product's bump, or the version files' own for a first release, or 0.1.0) and sets it itself, as one version commit on top of the work: in the product's main version files at their usual places (package.json and Cargo.toml at the top, tauri.conf.json at the top or in src-tauri), changing only the version, and in the product's own entries of the Cargo.lock beside a Cargo.toml. It then checks that commit: it changes only version files, and only their version, and every main version file says the new version. A file it cannot set or read stops the delivery with a plain message and nothing published. Main version files that do not follow the latest release stop for the coordinator. The checks run again on the version commit. Subfolders and other files are the reviewers' to check.
- **The Release Manager writes a release's notes.** It is the only agent at delivery, and only for releases. A release ships everything on the default branch since the previous release, from many tasks and agents, so its notes must cover all of it, which no builder knows. Petrina gives the Release Manager every commit from the previous release's tag up to the commit that ships, this task's included, each with its message (a task's commit carries its title, its summary and what changed for users); for a first release, every commit there is, the 200 most recent at most, saying so. It hands back only the notes, for users, grouped and in plain language. Petrina checks they are there and fit GitHub's limit, through the usual fix-your-result loop. It is read-only: anything it changes or commits is undone. Pull requests and commits to main need no agent: the plan's delivery step stays where it is and runs none for them.
- "Failed" publishes nothing in any mode: the version change goes, and the task goes back to the builder, review and the delivery check with a blocking finding. After two failures Petrina stops and asks.
- Petrina then publishes the exact tested commit: it pushes the task branch (never over other work already there) and opens the pull request; or pushes the default branch and the new tag in one all-or-nothing push, refused if the tag exists, and creates the release on that tag, only once GitHub shows the tag at the tested commit (Retry and "Ship it again" included); or fast-forwards the local default branch, only if it is still where Petrina saw it, and then pushes that branch to the saved GitHub address (never forced: if GitHub's branch has commits this computer does not, the push is refused, the coordinator pulls them into the main copy and retries, and the task counts as landed only once the push is through). Meanwhile it holds git's own lock on the main copy's staging area, so the main copy cannot switch branches halfway; if it switched just before, Petrina refuses and changes nothing. If the default branch moved before a release or local delivery goes out, Petrina brings the work up to date again, runs the checks again and, for a release, sets the version again and has the notes written again from the new list of commits (three times at most). A pull request is not prepared again.
- Each step is saved before it starts, and each product's credentialed steps (fetches, pushes and gh) run one at a time. Pause and cancel are checked when a step actually starts, not when it joins the product's line. Before reporting success Petrina checks the result on GitHub or in the main clone. Interrupted deliveries go through the one check under "Shipping is never repeated blindly".
- Fetches and pushes go to the GitHub address saved when the product was added; an old HTTP or git-protocol address uses HTTPS for the same GitHub repository, without changing the clone's settings. For a product added before Petrina kept it, the first step that needs it shows the current address once and asks whether it is the product's; the answer is kept. After a "No", Petrina does nothing for that product that needs a login; "Commit to main" still works, without the push.

## Architecture

```
apps/desktop            Tauri 2 shell + React UI
  src/                  UI (board, inbox, task sheet, session, agents, library, settings)
  src-tauri/            Rust host: starts the engine, notifications, single instance
packages/core           Domain model, scheduler, the flow rules, review numbers, demo simulator
packages/engine         The engine process (Bun): agents over ACP, git, SQLite, the local API
docs/                   This document and the UX notes
```

Inside the engine, `Engine` (`engine.ts`) is a thin front with the coordinator's commands. Each part of the work is a module of its own, sharing state and bookkeeping (lookups, the timeline, the inbox, saving) through the kernel (`kernel.ts`):

| Module | Owns |
|---|---|
| `driver.ts` | Scheduling, the task loop, checkpoints, recovery after a restart |
| `planning.ts`, `design.ts`, `work.ts`, `review.ts` | The stage kinds: plan, converge, do, review chain with verification |
| `turn.ts` | One agent working one step: its conversation, instructions, result and questions |
| `roles.ts`, `context.ts`, `prompts.ts` | Role contracts, what each role is shown, and the prompt around them |
| `product-checks.ts`, `checks.ts` | The product's checks and running them |
| `guide-keeper.ts`, `points.ts` | The review guide, and the files of points it shares with the learnings |
| `learnings.ts` | Lessons agents pass on, offered at the delivery check, written to AGENTS.md's Learnings section |
| `update.ts` | One commit per task, put on top of the latest main before the delivery check and before shipping |
| `shipping.ts` | Delivery, never repeated blindly, and pull request polling |
| `take-over.ts`, `terminal.ts` | Take over in the terminal |
| `tracking.ts`, `worklog.ts`, `codex-usage.ts` | The work log: an entry per agent turn and per notable moment, the permanent product list, each tool's limits, and the numbers each view asks for |

Built-in role contracts live in the engine's `roles.ts`, with their defaults in `@petrina/core`'s library. A role the coordinator adds uses the contract for its kind of result: notes or findings, with its saved wording and permission. The rules a task's run follows (board column, checkpoint wording, where a request for changes goes, how rounds end) live in `@petrina/core`'s `flow.ts`, shared by the engine and the demo simulator. Every command the window can send the engine is listed once, in `@petrina/core`'s `commands.ts`: the Engine implements them, the local API has one argument schema for each, and the window's two clients (the real engine's and the demo's) are built from the list, all held to it by the compiler.

- **Rust is a thin host.** It starts the engine, passes the engine's address and key to the window, and stops the engine it started when the app quits. It also shows the window's notifications, sets the count on the Dock or taskbar icon, and keeps Petrina to one running copy, with Tauri's own notification and single-instance plugins. The window gets none of those plugins' commands: only the shell's own three (the engine's details, show a notification, set the count), each refused to any window but the main one. No web client, no other plugins.
- **TypeScript holds everything domain-specific:** roles, plans, the scheduler, the engine, ACP handling, worktrees, SQLite, and the UI.
- `@petrina/core` never imports Tauri. It talks to a host interface, so the whole engine runs under Node in tests with fake agents.
- **State** is one snapshot in SQLite, saved shortly after every change and at once for anything the coordinator says. The UI and the engine read the same state, so tasks pick up where they left off after a restart.
- **Each task keeps its journey:** one entry per step, recorded the moment it starts (stage, round, reviewer position, role, profile, start and end, outcome, why the work moved on, and the questions and permission requests asked during it). Reviewers working together share a step per round, naming the profiles that actually start, including replacements; fresh voters and Petrina’s own checks and publishing have their own steps. A new round, send-back or retry is a new step; picking up after a restart or a pause continues the same one. A replacement agent gets a new step, keeping the first agent's tool, elapsed time and lines on its own step. Timeline and session lines carry the step they belong to. The journey is never trimmed the way the timeline and the conversation are. The engine and the simulator record it through the same helpers and words in `@petrina/core` (`journey.ts`), which also work out the steps still ahead from the plan; the screen only draws it.

## The engine process

The engine is one Bun process per Petrina folder (`~/.petrina`, or `PETRINA_HOME`).

- **One engine per folder.** The engine holds an exclusive SQLite transaction on `engine.lock` for as long as it runs; the operating system releases it the moment the process ends, crash included. A second engine finds it through the lock, or through `engine.json` for an engine started before the lock existed, and refuses ("already running"), or in app mode steps aside and hands over the running engine's address. The engine decides this, not the shell.
- **App mode.** The desktop shell starts `cli.ts app` with its stdin and stdout as a private line. The engine picks a free port, writes `engine.json` for scripts, and says it is ready in one JSON line on stdout; that line, with the key, never goes to a log. Everything else the engine prints goes to `engine.log`, written only by the engine that holds the folder. When stdin closes (the app quit, crashed or was force-quit) the engine stops its agents the way pausing does, saves, removes `engine.json` and exits; the shell forces it after 8 seconds. An engine the app did not start is left alone. Started from the Dock, the engine asks the login shell for the PATH the terminal has.
- **The key.** The window asks the shell for the address and key through a Tauri command that only the main window may call (`capabilities/default.json`), keeps them in memory, and presents the key as a WebSocket subprotocol when the connection opens. The engine refuses any request with the key in its address, a wrong or missing key, and pages that are not Petrina's own.
- **Restarts are safe.** Everything the coordinator says during a step (messages, answers, the note with a "No", the change request that started the step) is saved before any agent sees it, and kept on the task until the step hands back its result. An agent that starts the step again gets all of it, in order, in its opening instructions. The window keeps what it sent until the engine confirms it, and sends it again after reconnecting, with an id so a resend counts once.
- **Agents pick up where they left off.** The moment an agent's conversation opens, the engine saves a note of it on the task: the step (stage, design round, reviewer position), the role, the tool and model, the conversation's id, and the working copy's commit when the step first started. The note goes when the step finishes or fails, or the coordinator pauses, cancels or asks for changes; stopping Petrina keeps it. After a restart, a step whose note matches its step, role, tool and model reopens that conversation in the same working copy, with resume, or load when that is all the tool offers (what load replays is not shown again). Model, effort and the automatic safety mode are set again, mode last, and the agent's environment is the same as for a new conversation. The agent gets one line (Petrina restarted, the stage, the last thing it was doing, check the working copy and continue), then only what it has not heard: the answer to its open question and messages still in line. The timeline says "Picked up where it left off". When the conversation cannot be reopened (the tool cannot, it is gone, an error, or no answer within a minute), a fresh one starts with the usual opening instructions plus where it was: the stage and role, its last 10 activities in the step, and up to 30 files added, changed or removed since the step started. The timeline says "Started this step again" with the reason. A question open at the restart stays in the inbox without holding a slot, and its answer goes to the conversation that asked it, once; an open permission request is dropped with a note, and the agent asks again if it still needs to. A read-only role's clean-up goes back to the commit from when the step first started. The Release Manager never reopens a conversation, and pausing, resuming and "Try again" start the step fresh. Reviewers and voters working side by side are never reopened either, so stopping the engine by hand (Ctrl-C or SIGTERM on `petrina serve`) first drains: no new agent starts, waiting tasks say "Petrina is restarting", and those agents and a Release Manager mid-delivery get up to four minutes to hand back; a second Ctrl-C stops at once. The app closing its engine stops it at once, so a relaunch never finds the folder busy.
- **One commit per task, on top of the latest main.** After every build Petrina folds the branch into one commit on top of where it forked, under the builder's title in the repository's own style, so the repository's commit-message rules see what will land. Right before the delivery check, and again right before it gets the delivery ready, Petrina puts that commit on top of the latest default branch itself (from GitHub for pull requests and releases, the local branch for "Commit to main"), with `git merge-tree` and `commit-tree`, which never leave a working copy halfway through a rebase (`packages/engine/src/update.ts`). Clean: the checks run on the result, and the delivery check shows it. Overlapping: the working copy is put on main with the change applied, conflict markers and all, and the builder brings it up to date (it learns what main changed from its commits, ports the change, leaves no markers, runs every check). The same happens at the start of every review round, so a conflict is found before any reviewer spends time and a port after a review stays the exception. When a port does follow a review, the change itself was reviewed already: one reviewer, on a tool other than the builder's where the stage has one, reviews only the port (`git range-diff` between the reviewed version and the ported one, and each resolved file against main's), as one round; its findings go back to the builder as usual, and the rounds after it are ordinary. The coordinator's approval still resets after a port, because the change was rewritten by hand. Nothing at delivery rebases, merges or changes code; for a release Petrina adds only its own version commit. Petrina delivers the result itself, as a fast-forward, a pull request or a release.
- **Learnings in AGENTS.md.** The builder, reviewers and testers can pass on, with their results, what they learned about working in the repository (how to build or test it, a trap, an unwritten convention): one line each, at most three, never about the task itself. Petrina keeps them on the task, without repeats or lines AGENTS.md already has, and at the delivery check offers them in one inbox item, without holding anything up. Accepted ones join the "Learnings" section of AGENTS.md with the next delivery, in its one commit (`packages/engine/src/learnings.ts`). Petrina adds nothing to agents' prompts for this: Claude Code and Codex both load AGENTS.md by themselves, so a session Petrina starts and one the coordinator starts in the repository know the same things.
- **The builder keeps its conversation.** A fix round, or bringing work up to date, goes back to the builder's own conversation from its last step (same tool and model), so it keeps what it learned, compactions and all, and hears only its job now and where things stand. The round where it is asked to step back and rethink starts fresh on purpose. When the tool cannot reopen it, a fresh conversation gets what the builder reported last time.
- **Shipping is never repeated blindly.** Petrina publishes, and saves each publishing step before it starts. One check runs before Petrina publishes, and again after any interruption (a quit, a crash, a pause, a failed step and its Retry, a cancel): it looks for the pull request from the task branch at the tested commit, the release on the saved tag at that commit, or the work on the local default branch. Releases published before this delivery started never count. It asks GitHub about the product's own repository, from outside the working copy, so a remote an agent rewrote cannot fake a delivery, and it first makes sure the login can see that repository: GitHub answers "not found" alike for a missing release and a repository the login cannot see. Found: it is recorded. Clearly not there: Petrina carries on with the saved step; pushing the same commit again overwrites nothing, and GitHub refuses a second open pull request for a branch, a second tag and a second release. GitHub unreachable, or something else there: Petrina publishes nothing more on its own and the coordinator decides ("Check again", "Ship it again", which gets it ready again and still runs the check, or "Mark as done"). A cancelled task stays cancelled, but what went out keeps its link; if GitHub cannot be asked then, Petrina asks again every minute and after a restart. A delivery saved by a Petrina from before this design, whose delivery agent published it itself, is never acted on by Petrina: no check, no update from GitHub, no preparation. The task shows "This delivery was interrupted before Petrina was updated: check GitHub, then choose", with "It went out (mark as done)" and "Ship it again" (a fresh delivery, from the delivery approval as the task sets it), and nothing happens until the coordinator picks one. Cancelling it keeps the note on the task.

## Take over in the terminal

The coordinator can drive a step's agent by hand, in their own terminal:

- **Take over.** Allowed while an agent other than the Release Manager works or waits on the coordinator, on Claude Code, Codex or Grok, in a conversation that already has its instructions (`takeOverBlock` in `@petrina/core`). Petrina checks it can open a terminal and that every value fits in a launcher, then stops the agent and waits for its process to exit. Open questions and permission requests go. An editing role's uncommitted work becomes one commit marked as its unfinished work; a read-only role's is undone. Petrina notes the commit the task is on, keeps the step's conversation note, and the step keeps its seat in the pool (it counts toward its tool's cap) with "You're driving" in the inbox. Pause, Cancel and the inbox actions wait for the hand back; a restart keeps all of it.
- **The launcher** (`packages/engine/src/terminal.ts`). One small script in `takeover/<task>/` in Petrina's folder (`0700`): `open.command` on macOS, `open.sh` on Linux, `open.ps1` on Windows. It starts the tool Petrina found on PATH in the working copy: `claude --resume <id> --model <model> --effort <effort> --permission-mode manual` (`default` when the installed copy's help does not list `manual`, as before Claude Code renamed it), or `codex resume <id> --model <model> -c model_reasoning_effort=<effort> --sandbox workspace-write --ask-for-approval on-request -c approvals_reviewer=user --no-daemon`, or `grok --resume <id> --model <model> --effort <effort>` (Grok's usual prompts; never always-approve). The adapters' conversation ids are the ids the apps reopen (the Claude Agent SDK's session id, Codex's thread id, Grok's session id). Every value is checked against a strict pattern first (absolute paths without quotes, `$`, `;`, `&`, `|`, `%` or line breaks; a UUID; a model name; an effort; the permission mode), and nothing typed by a person or an agent goes in. The Windows launcher starts with a UTF-8 byte order mark, so Windows PowerShell reads accented folder names as written. Each copy of the launcher keeps a record (`run.<pid>`: its process id and start time) while it runs. Only one copy opens the tool: on macOS and Linux it takes a `lock` that appears holding its record in one step (a hard link), and one left by a copy that is gone is taken over the same way, in a file named after that copy (`lock.after.<its record>`), so however many copies find it at once only one takes it. No copy removes a lock, not even its own when it ends (the next copy takes over after it), so none is ever taken twice: a copy that was slow to check on one that has since closed finds the lock after it already taken; on Windows it holds the `lock` file open for itself, which the system lets go of when it ends. Every other copy, even one started at the same moment, says the tool is already open and stops. The copy that opened the tool writes `state=ended` when it exits, or when its window is closed. The terminal gets the coordinator's environment minus Petrina's own variables.
- **Terminals.** macOS: Terminal by default, iTerm2, Ghostty, WezTerm, Alacritty or kitty when installed (`open -a`). Windows: Windows Terminal, else a PowerShell window. Linux: `xdg-terminal-exec`, `x-terminal-emulator`, the desktop's own (GNOME, KDE, Xfce, MATE, LXDE), then common ones; none without a display. The coordinator's choice is kept in the state. Copying the command runs the same launcher.
- **Hand back.** Refused while any copy's record shows it running (pid alive with the same start time, so a reused number does not count); "anyway" only when Petrina cannot tell (no copy reported starting since the terminal was last opened, or a record can't be checked). Take over, Reopen terminal and Hand back run one at a time per task, and Reopen terminal clears the last session's end first, so an earlier "it has closed" never lets a hand back through while the terminal opens again. Refused when the working copy is off the task's branch or a merge, rebase, cherry-pick or revert is half done. What is left uncommitted becomes one commit marked as the coordinator's. The note (the agent's saved work, commits, up to 10 files, the coordinator's note) goes into the session, the timeline and the task's notes, and onto the conversation note, whose commit moves to the new head so a read-only role's clean-up keeps the hand changes. The launcher folder goes. The same driver starts at once: the step's conversation reopens and hears the note, or a fresh one gets its usual instructions plus the note.
- **Review after hand changes.** If files changed, the tamper check runs on the whole branch at once and the task is marked as having hand changes; the delivery check and the delivery step never start while that mark is set, and it clears only when a review chain starts from its first reviewer. A chain still ahead covers the changes. Otherwise the chain being driven, or the last one behind, runs again from its first reviewer once the driven step finishes, without using up a round.
- **How it was checked.** macOS: by hand with the real Claude Code and Codex, in Terminal. Linux: Petrina's own launcher in every terminal it finds (the system default ones, Console, GNOME Terminal, Konsole, Xfce, MATE, LXTerminal, kitty, XTerm), on a virtual screen in a container. Windows: the `open.ps1` launcher run by PowerShell 7 in a container; Windows itself is not checked yet.

### Needs a real device: Windows

These do not block shipping. Run them once a Windows PC is available:

1. Take over a Claude Code agent and a Codex agent with Windows Terminal installed: a new Windows Terminal window opens in the task's working copy, on the agent's conversation with its history.
2. The same without Windows Terminal: a Windows PowerShell 5.1 window opens instead.
3. With an accented letter in the user's folder or the product's path (say `C:\Users\José`): the app still opens in the right folder.
4. Close the app: Petrina says it has closed, and Hand back works. Close the window with the app still open: the same.
5. Run the copied command twice at once, and click Reopen terminal while the app is open: only one copy of the app runs, and the other window says it is already open.
6. Claude Code and Codex installed through npm (`claude.cmd`, `codex.cmd`): the launcher starts them with every option intact.

## Security model

Agents start with full permissions inside their own working copy; the coordinator asked for that, and it keeps the squad fast. What stops them doing harm is layered, and it is important to know which layer is the boundary:

| Layer | What it guarantees |
|---|---|
| **The tools' own checkers** | Claude Code's Auto mode, Codex's Auto review and Grok's auto mode decide what is safe to run; Codex also keeps its own workspace sandbox. Petrina does not second-guess them or re-implement them. Grok starts with `--permission-mode auto` and session auto mode, never an always-approve flag, so a saved always-approve setting does not replace the checker. |
| **Logins** | Agents act with the coordinator's own logins: they get the coordinator's normal environment with nothing stripped, so gh's login, git's credential helpers as configured, SSH, AWS (the aws CLI, `~/.aws` and its SSO caches), the Azure CLI (`~/.azure`) and Azure DevOps (`az devops`, and git to dev.azure.com and visualstudio.com through the coordinator's credential manager) all work. Only prompts are switched off (`GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`) so nothing hangs, and windows stay closed (`BROWSER=none`, `PETRINA_AGENT=1`). Agents can therefore read and, in principle, write GitHub and the coordinator's other accounts. Every agent's instructions say to read and investigate freely and never to push, open, merge, close or comment on pull requests, create releases or change anything on GitHub, nor publish, merge or change other shared resources unless the task asks for it. That rule rests on those instructions and the tools' checkers, not on Petrina. |
| **Petrina publishes** | Petrina publishes deliveries with its own code, never a shell: it pushes the exact tested commit and opens the pull request, sets a release's version in a commit of its own that it checks, pushes the default branch and the new tag together and creates the release on that tag, or fast-forwards the local default branch. No agent works at delivery except the read-only Release Manager, which only writes a release's notes. It has no merge, force-push or delete. Titles, descriptions and release notes stay text. |
| **Petrina's own git steps** | Never run hooks or the file monitor, whatever an agent wrote into the repository's settings. Only fetching, pushing and gh use the coordinator's normal git and GitHub setup, and only right after the repository's own settings pass an allowlist, so a credential helper, SSH command, address rewrite, proxy or include an agent planted stops them. Fetches and pushes name the address saved when the product was added, never a remote, so a changed remote or push address cannot redirect them. Pushes are never forced and carry only the refs Petrina names: no tags followed, no submodules. gh runs from a neutral folder, pinned to the product's repository. Each product's credentialed steps run one at a time, the update before a delivery included. Everything that touches a working copy, the product's checks and the repository's commit hooks run without credentials. |
| **Gates** | Plan, design and delivery checks live in the engine and decide what Petrina itself publishes. No agent's answer can skip them or grant permission to publish: that is the coordinator's approval, or the task's own setting to deliver without asking, for the approved change, delivery mode and destination. They do not stop an agent that disobeys its instructions from using the coordinator's logins directly. |
| **Read-only roles** | They run in the tool's automatic mode too, so they could change files: every change and commit they leave behind is undone when their stage ends, however it ends. What the coordinator changed while driving one is kept. |
| **Take over in the terminal** | Not a Petrina boundary: it is the coordinator acting with their own setup and logins, in the tool's normal mode with its usual prompts, where some actions may run without a prompt. Petrina adds no blocks there and does not change their GitHub access, connectors or plugins. It only keeps credentials, its engine key and its own variables out of the launcher, its command lines and the terminal, and makes sure delivery through Petrina still goes through review. |

Known limits: anything done in a take-over session (a push, a pull request, a connector action) happens for real without Petrina's review, and Petrina does not notice it; someone can also reopen the conversation by hand in another terminal after handing back, and Petrina only tracks the sessions it opened. Agents run as the coordinator's user and act with the coordinator's logins. "Never publish without approval" for agents rests on their instructions and on Claude Code's, Codex's and Grok's own checkers; Petrina's gates decide only what Petrina itself publishes. Saved logins, settings in the home folder, Petrina's own connection file and its approval controls are only as protected as the tools' checkers keep them. Petrina adds no operating-system boundary.

## Security notes

- Agent output is untrusted. The UI renders it as text only (no HTML, no `dangerouslySetInnerHTML`). Links are opened only when they are `https://` and only through the host.
- Petrina runs each product's checks itself, outside the tools' safety checkers (see `AGENTS.md`). Reviews, the tamper check and the review guide compare against the base commit pinned when the working copy was made, never a ref an agent could move.
- Agents get the repository's content as context. Treat it as untrusted input to the model: approval gates and permission decisions are enforced in code, not by prompting.
- Every result from an agent is validated against a schema before it changes state. IDs coming from agents are validated before use.
- Round limits and time limits cap every loop.
- The window has a strict Content Security Policy and only the Tauri permissions it needs.
- CI uses read-only permissions and actions pinned to commit SHAs.
