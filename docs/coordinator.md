# Coordinate projects through Petrina

This guide is for an external coding agent acting on a human's behalf to coordinate product work through Petrina's CLI or MCP server.

Your job is project coordination: turning human goals and reports into well-scoped tasks, ordering the Backlog and Queue, handling Inbox checkpoints and questions within delegated authority, and verifying evidence before shipping. You are **not** developing Petrina, auditing its engine internals, profiling tool adapters, editing product code inside Petrina's working copies, or supervising every command an admitted agent runs.

Use [the CLI and MCP reference](coordination.md) for installation, MCP setup, argument schemas, pagination and event-stream syntax. When developing Petrina itself, follow [AGENTS.md](../AGENTS.md) and [docs/design.md](design.md) instead.

## Responsibilities and boundaries

- **Understand the human's mandate.** Before changing the board, confirm the human's goals, priority order, target products (`product list`, `product inspect`), starting branch or pull request (`startFrom`), delivery mode (`pull-request`, `release`, `local`), approval gates (`approvePlan`, `approveDelivery`, `shipLowRisk`), and what tool permissions or screen use are already authorized.
- **Clarify only material missing decisions.** Check the product repository, existing tasks (`task list`, `task history`) and documentation first. Ask the human only when a genuine product choice, scope trade-off or ungranted permission cannot be resolved from evidence. Ask one plain-language question at a time with your recommended option first.
- **Maintain clear, evidenced requests.** Write task titles and descriptions (`task add`, `task update-backlog`) in plain language with explicit product scope, desired user or system outcomes, and concrete acceptance criteria. For bugs, include reproduction steps, observed versus expected behavior, and supporting check or code evidence.
- **Investigate uncertain reports before treating them as defects.** When a report or failure is ambiguous, inspect the product repository, recent history or check diagnostics read-only first. Distinguish confirmed defects from questions, environment issues or already-resolved behavior. Never present an unverified hypothesis or an unrun check as a confirmed bug.
- **Deduplicate and group related requests without losing scope or provenance.**
  - Search current tasks (`task list`) and finished or cancelled work (`task history`) before filing a new request.
  - Group related Backlog items only when they belong to one coherent change, share identical product, starting-point and delivery choices, and have no unresolved or conflicting dependencies.
  - When consolidating unstarted Backlog cards (`task update-backlog` or `task add --backlog` followed by `task cancel` on superseded cards, or combining in the app), keep every original request's scope, acceptance outcomes, bug evidence and provenance (original task IDs and finding context). Never drop requirements or edge cases just to shorten a card.
- **Prioritize Backlog and explicitly queue reviewed work.** Stage drafts or multi-part intakes with `task add --backlog`, refine them with `task update-backlog`, and admit reviewed tasks explicitly with `task queue`. Order queued work with `task reorder` (`--position` or `--anchor-id` with `--side before|after`), hold or release queued tasks with `task hold` and `task unhold`, or return an unstarted queued task to Backlog with `task backlog`.

## Required extra full validations

Arrange genuinely necessary extra full-suite validation with `validation run` ([request and evidence details](coordination.md#required-extra-full-validation)), currently only an owned local Linux container using a prepared local image. The immediate reply names the exact saved commit/tree and excludes working edits; hand new work back to Petrina to save before requesting it. Retry the same request reference after a lost reply. Never pause the pool to reserve check room or watch other processes for a gap. Focused tests and local image preparation remain normal coding-tool work. Extra results never replace configured full delivery checks or change their workers, assertions or deadlines. If cleanup is held, make the container service available or stop the named container, then let Petrina confirm it. If Petrina cannot establish that a saved client process number still belongs to the run, do not stop programs by that number. Checks stay held; save your work and restart the computer if the uncertainty persists, then let Petrina retry confirmation. Product removal is refused while queued/running/stopping/held extra work still needs the ownership record.

## Dependencies and starting points

- **Real prerequisites versus coincidental file overlap.** Set `after` prerequisites (`task add --after` or `task dependencies --after`) only when a task genuinely needs another task's changes to land first—such as a schema, contract or shared foundation that downstream work builds on. Do **not** chain tasks merely because they touch the same or nearby files. Petrina gives each task its own Git worktree, folds each build into one commit on top of where it forked, updates that commit onto the latest approved source at the start of each review round and before delivery, and routes real merge conflicts through the Builder and a focused port review. Unnecessary dependencies serialize work that the pool could run in parallel.
- **Choose the prerequisite control for the task's progress.** Before work starts, use `task dependencies` while the task is in `backlog` or `queued`. For a genuine prerequisite discovered after work starts, use `task wait --task-id TASK --after '["FIX"]' --reason "Why this fix must land first" --request-id REFERENCE` (MCP: `petrina_task_wait`). Pass the complete list, up to 20 tasks; `[]` with a reason clears a runtime wait. Petrina rejects unknown tasks, self-dependencies and loops across both kinds of prerequisites. Runtime waits cannot name already-finished tasks or be set on finished tasks or tasks awaiting merge.
- **Let a running task wait at its next safe boundary.** A runtime wait saves immediately. Admitted agents and their in-session helpers, checks and deliveries finish; unstarted participants and subsequent work wait, freeing their slots. Existing Inbox checkpoints remain answerable. Other tasks, including ones on the same product, continue. Use this control instead of pausing the pool and keeping an external resume condition. Never derive prerequisites or blocker kinds from report wording.
- **Resolve runtime waits explicitly when a prerequisite does not land.** Runtime waits require recorded landing for every publishing product. Cancelled, combined, closed without merging, marked-done, no-change and unpushed results do not release them. Inspect the saved reason and prerequisite states; when a wait needs your decision, revise the complete list or clear it with a reason and a new request reference. Each change remains in the task's record. Once released, Petrina updates the work to its current approved starting source and applies the ordinary checks, reviews and delivery approvals. Waiting consumes no repair or review round and does not itself reset a conversation.
- **Understand the existing pre-start release rules.** A prerequisite holds its `after` dependents while its state is neither `done` nor `cancelled`, and—on a shared (multi-product) task—while any product still has an open pull request (`pull-request-open`), a pull request closed without merging that has not been accepted (`pull-request-closed` with `decision: "needed"`), publishing in progress (`publishing`), or a local commit whose push has not finished (`local-unpushed`). Once a prerequisite is `done` or `cancelled` with none of those per-product holds, the scheduler releases the dependent task—even if the prerequisite finished without landing (`cancelled`, `no-changes`, a single-product `closed` pull request, a shared `closed` pull request accepted with `mark-done`, or a single-product `marked-done`). When a prerequisite finishes without landing, Petrina records that fact on the dependent task; inspect the dependent before it runs to confirm its scope and starting point still make sense.
- **Preserve product, source and delivery choices.** Keep approved product selections, `startFrom` (`default`, `branch`, `pull-request`) and `delivery` (`pull-request`, `release`, `local`) choices intact unless a change is required. Updating an unstarted task's source (`task source`) validates the source asynchronously; if rejected (`invalid`), the previous approved source remains in place and correcting it requires a new `requestId`. Always inspect the plan request again after changing a task's source.

## Proactive Inbox handling

Handle Inbox items (`inbox list`) promptly within your delegated authority, but **never approve blindly to empty the Inbox**. Before deciding any item:

1. Inspect it with `inbox inspect`, `learning inspect` or `review-guide inspect`.
2. Follow every `next` cursor (`--cursor`) when `shortened` is present so you read the complete recorded evidence.
3. Verify `kind`, `revision`, `choices`, `recommendation` and `decisions`.
4. Submit your decision with the exact inspected `revision` and a saved `requestId` (`--request-id`). If the request changed (`outcome: "changed"` / exit code 5), inspect it again before deciding.

| Kind | What to verify and how to decide |
| --- | --- |
| **Plan (`plan`)** | Check the selected products, validated `source` and `proposedSource`, risk level, stages and profile assignments. Confirm any planner-proposed products, permanent clone folders, branches or pull-request targets match the human's intent. Adjust future stages (`plan assign`, `plan add-reviewer`) or unstarted source (`task source`, then re-inspect) if needed. Approve (`inbox approve`) or send back with guidance (`inbox changes --note`). |
| **Design (`design`) & Disagreement (`disagreement`)** | Read the brief, acceptance checklist and objections (`inbox inspect`, `task read --section design`). On a `disagreement` where the Architect and Design Reviewer reached the round limit, read both sides and either side with the Architect (`inbox approve`) or record your call (`inbox changes --note`), which settles the objections so the Architect updates the brief before the design check. At `design`, approve (`inbox approve`) when the brief and acceptance criteria match the request, or request revisions (`inbox changes --note`). Escalate material product or UX trade-offs to the human. |
| **Question (`question`)** | Blocking (`blocking: true`): the agent holds its pool slot while waiting. Read the question and `choices` (`recommendation` is listed first). Answer (`inbox answer --answer`) when repository evidence, task scope or the human's mandate settles it; escalate genuine product decisions to the human. |
| **Permission (`permission`)** | Blocking (`blocking: true`). Inspect the exact command or action flagged by the tool's safety checker. `inbox allow` permits it **once only** (nothing is remembered for later turns or tasks); `inbox deny --note` blocks it. Allow routine, in-scope build or test actions within the human's authorization; deny or escalate destructive commands, credential exposure or shared-resource changes outside the task's mandate. |
| **Screen (`screen`)** | Quiet and non-blocking (`screen inspect`, `screen allow`). Agents work headlessly in the background and ask for the screen only when a check requires a visible window, menu bar, Dock or live desktop interaction. Grant `screen allow` (or set `screen set --mode off\|hour\|on` or `screen task --allowed`) only when the human permits screen use and the check cannot be performed offscreen or headlessly. |
| **Failed or interrupted automated checks (`delivery` check problem)** | Raised after two automatic Builder repair returns fail to produce a passing automated product check or commit hook, or when an automated check is marked unverified/interrupted. `inbox approve` is unavailable; `decisions` offers `inbox.rerun-checks` and `inbox.changes`. Read the original diagnostics (`journey check`) and Builder answers. Use `inbox rerun-checks` after resolving an external or power interruption (reruns automated checks without granting extra automatic repair returns and resumes the workflow only on a pass), or `inbox changes --note` to give the Builder one targeted repair turn. |
| **Exhausted or unverified acceptance (`delivery`)** | When automated checks pass but Tester acceptance checks still fail after two Builder returns, or a required item (saved checklist or requested proof) could not be verified (`blocked`), the task stops at the `delivery` checkpoint, added even when delivery approval is off, where `decisions` offers `inbox.approve` and `inbox.changes` (`inbox rerun-checks` is refused because no automated product check failed or was interrupted). Inspect `acceptance.evidence` for recorded counts, problem reasons and per-product version coverage, even without a design brief. Follow its testing-step, original-report and exact-input links as needed, and read every shortened inspection page. Unavailable checks keep their recorded meaning; the request's scope is separate. Earlier runs and later unfinished attempts are linked without being combined. If an item was blocked by missing screen access or setup, enable it and use `inbox changes --note` so verification runs again; if a real acceptance failure remains, send concrete repair instructions with `inbox changes --note`; approve (`inbox approve`) only when the human's mandate accepts the recorded evidence; approval keeps the items unverified. |
| **Exhausted review rounds (`delivery` with `reviewDecision`)** | Raised when review rounds stop making progress with Important findings still open. Inspect the findings and verifier votes (`task read --section findings`, `journey finding`). Prefer `inbox changes --note` with concrete repair instructions when a real defect remains; use `inbox approve` to continue to final verification only when the evidence shows the remaining dispute does not violate the human's quality bar (current product checks, acceptance testing and a separate version-bound delivery check still follow). |
| **Stuck (`stuck`)** | Read `task inspect`, `task read --section error`, `tools inspect` and `task activity`. If a tool sign-in, quota window, refused local-delivery push (`local-unpushed`), or transient failure has cleared (`tools check`), run `inbox retry` (`inbox recovery` is refused on `stuck` items). Cancel obsolete tasks (`task cancel`) or escalate persistent account or login blockers to the human. |
| **Delivery recovery (`shipping`)** | Raised when publishing was interrupted and Petrina cannot confirm whether the work went out (`publishing.result` kind `interrupted`), or when a shared task's pull request was closed without merging. Inspect the task and verify GitHub or local repository state before calling `inbox recovery --decision check\|ship-again\|mark-done`. Prefer `check` (confirms whether the tested commit already reached the target; unavailable on legacy carried-over deliveries, which must be checked on GitHub first) or `ship-again` (re-prepares and runs Petrina's idempotency check before publishing). `mark-done` behaves differently for single-product and shared tasks: on a **single-product** task, it closes the task as `done` without confirmed delivery and permanently records landing as `marked-done` (`unconfirmed`); on a **shared (multi-product)** task, `mark-done` is refused unless a product's pull request was closed without merging (`decision: "needed"`), and when allowed it marks those closed pull requests as resolved (`decision: "accepted"`, not `unconfirmed`)—returning to waiting if other deliveries are unfinished, staying at `pr-open` while any companion pull request remains open, or finishing the task as `landed` once all other products are delivered. |
| **Learning offers (`learnings`) & Review-guide proposals (`guide`)** | Inspect with `learning inspect` (zero-based `positions`) or `review-guide inspect`. **Investigate every proposed line** against the repository's current `AGENTS.md`, `REVIEW.md`, documentation, scripts and code—never auto-accept or auto-decline. Accept (`learning accept --positions '[...]'` or `review-guide accept`) only verified, durable, reusable rules that help unrelated future tasks and are not already covered. Decline (`learning decline`, `review-guide decline`, or omit unselected positions) product bugs (file a Backlog bug task instead), current feature/UX contracts (belong in `docs/`), task history, delivery summaries, acceptance checklists, one-off investigations or temporary machine conditions. Petrina writes accepted points on a shipping branch. |

### Requests to load the shared computer

Handle a request under the [shared-host load rules](testing.md#shared-host-load-diagnostics) as an ordinary blocking Inbox question: the asking agent keeps its pool place while waiting. Review its proposed limits and cleanup, then arrange any quiet time with the person using the computer, for example by letting active check runs finish and holding queued tasks. Pausing the whole pool needs the person's approval and still lets admitted agents finish their steps.

Answering yes reserves nothing: admitted agents and their later checks, other products and the person's own programs keep running. There is no atomic control for a quiet window. Use `inbox answer --answer` to give the agreed resource, process and time limits. Answer once the window is ready, or give a fixed clock time; do not ask the agent to watch other work for a condition such as "after the other checks finish". Alternatively, decline so the agent reports what it could not check. Other tasks' check failures remain ordinary failures; the experiment does not automatically explain or excuse them.

## Operations, ownership and monitoring

- **Use the supported CLI and MCP operations.** Coordinate through the named CLI commands (`petrina <group> <verb>`) or MCP tools (`petrina_<group>_<verb>`) described in [docs/coordination.md](coordination.md), using `--help` or `tools/list` for exact schemas. Prefer named operations over legacy `state` and `do`. Never edit Petrina's SQLite database directly, never copy or log the connection key from `~/.petrina`, never edit files or run Git commands inside Petrina's task or reviewer worktrees, and never push, open pull requests, tag releases or merge on Petrina's behalf.
- **Preserve request references for safe retries.** Supply and save a `requestId` (`--request-id`) before every mutating call. If a reply is lost or disconnected, retry with the **identical** `requestId` and arguments to retrieve the saved receipt. When changing arguments, recovering from an `invalid` source choice, or acting after a `changed` revision, inspect again and use a **new** `requestId`. If `task source` or `inbox retry` is interrupted after returning `pending`, inspect the task before sending a new request.
- **Let Petrina own execution.** Petrina manages pool admission, usage-aware profile balancing and stand-ins, worktrees, single-commit folding, automated product checks and commit hooks, blind parallel reviews, verifier voting, and publishing. Send mid-turn guidance (`task message --mode now|queue|interrupt`) only when course correction is needed.
- **Do not disrupt the engine as routine coordination.** Do not call `engine pause`, `engine stop` or `engine restart` during ordinary coordination unless requested by the human or covered by your mandate. `engine pause` closes new admissions across the entire pool while admitted steps drain; use `task pause` when you only want to interrupt one task.
- **Monitor with workflow events, then read focused evidence.**
  - Capture a starting cursor (`watch events --timeout-ms 0 --json` or `petrina_watch_events` with `timeoutMs: 0`) before acting, then wait on `watch events` (or `watch wait` for targeted conditions) with a deadline safely below your host's tool timeout. Pass the returned `cursor` on each subsequent call. If `continuity-lost` is returned after a restart or expired window, inspect current state (`task list`, `inbox list`, `task inspect`) and continue from the new cursor.
  - Rely on the compact facts and `refs` in workflow events (`seat.started`, `seat.finished`, `check.finished`, `check.reused`, `review.finished`, `repair.returned`, `coordinator.request`, `publishing.result`, `task.finished`) instead of polling full board snapshots or re-reading whole transcripts. Read focused evidence (`journey check`, `journey finding`, `journey result`, `journey input`, `journey review-input`, `task conversation --if-revision`, `task activity`, `watch event`) only when a transition, failure or checkpoint warrants investigation, and follow `next` cursors to the end.
  - **Distinguish a long or quiet step from a confirmed failure.** Routine tool executions, streamed text and clock ticks never emit workflow events, and a `timed-out` wait with an empty batch simply means work continues past that wait deadline. Before treating a quiet step as stuck, check `task health` and `task activity` (`working`, `workedMs`, `runningTool`, `lastObservedAt`, `waitingReason`, and any historical `estimate`, which is a median reference rather than a cutoff; note that `turnEndedAt` only means turn observation ended, not that a tool finished). Do not retry, pause or cancel healthy work that is still making progress.

## Delivery and landing decisions

- **Require recorded evidence, not Builder claims.** A Builder's summary or finding answer ("fixed", "tests pass") is a claim, not a current check pass. Delivery requires Petrina's own recorded check evidence (`checks.basis` of `ran` or current `reused` on the exact commit and check/hook definitions, or `none-configured` when none exist) and a completed review (`review.examined: true` with no open Important findings).
- **Separate unverified checks and acceptance from confirmed defects.** When an automated check is marked interrupted by a recorded machine power event (`checkProblem: "unverified"`), use `inbox rerun-checks` to run the automated checks afresh rather than treating the interruption as a code bug. When a Tester acceptance item could not be verified (`blocked`, for example because screen access or an external service was unavailable), it stops at the `delivery` checkpoint (`inbox.approve` or `inbox.changes`, since `inbox rerun-checks` only reruns failed or interrupted automated product checks)—grant or restore what the check needed (`screen allow` or environment setup) and use `inbox changes --note` to re-verify, rather than blaming the implementation without a reproduced failure.
- **Track unrelated older bugs as follow-ups.** Confirmed `Pre-existing` findings do not block the current task; when the task finishes, Petrina turns confirmed unrelated older bugs into deduplicated Backlog follow-up cards with their reproduction, evidence and provenance links. A report of the same bug as an unfinished bug task you created for exactly its products, even one already queued or running, is added to that task instead, without changing its request, products or work. If you find an unrelated defect yourself during investigation, add it to Backlog (`task add --backlog --kind bug`) rather than expanding or blocking the active task.
- **Record bugs tracked by hand.** After filing or finding a confirmed older bug yourself that Petrina left “Not tracked”, use `task track-finding --task-id SOURCE --finding-id REPORT --target-task-id BUG --request-id REFERENCE` (MCP: `petrina_task_track_finding`). This also works for source reports in History. The source must be done with complete reproduction and evidence and a settled untracked outcome; the target must be another non-cancelled bug task covering all reported products. Open targets gain the report and its pictures without changing their request. Finished targets stay unchanged and cannot receive a report while original pictures remain. The action waits for automatic linking and can finish an interrupted picture copy to the card already holding the report; it refuses a different target even after that card moves to History. It records the link with its retry receipt and runs no agents or new card creation. Inspect a refusal before trying changed arguments with a new reference.
- **Respect full checks and review gates.** Affected-test reports and focused Builder checks are feedback aids only; delivery requires the full configured product checks, commit hooks, applicable security review and blind review convergence on the integrated tree.
- **Distinguish task `landing`, per-product `publishing.result`, `shared` state, `watch wait --condition landed` and dependency release.**
  - **Not finished (`landing: "open"`, per-product `pending` or `publishing`):** Task `landing` is `open` whenever the task has not finished yet (including planning, building, review, active publishing, or an unpushed local commit while the task is still open). Per-product `publishing.result` reports `pending` before publication starts and `publishing` (with the active `step`) while shipping is in progress.
  - **Awaiting PR merge (`landing: "awaiting-merge"`, `publishing.result` kind `pull-request-open`, task state `pr-open`):** Petrina pushed the branch and opened or updated the pull request (`deliveryConfirmed: true` in `task inspect`), but `landed` is `false`. It satisfies `watch wait --condition delivered`, **not** `watch wait --condition landed`, and keeps `after` dependents blocked until the pull request merges on GitHub. **Petrina never merges a pull request**, and you must not merge it unless the human explicitly authorized that action outside Petrina.
  - **Confirmed landing (`landing: "landed"`, `publishing.result` kinds `released`, `committed`, or `merged`):** The change reached its destination: a published release (`released`), a recorded branch commit (`committed`, which has `landed: true` whenever `landed` is recorded—with `pushed: true` when push confirmation is recorded, or without it on local-only/older records), or a merged pull request (`merged`). `watch wait --condition landed` completes only when the task's displayed `landing` is `landed` (note that on a shared task, inspect per-product `publishing.result` and `shared` in `watch events` as well, because an unpushed commit on a non-displayed product still blocks dependents).
  - **No product changes (`landing: "no-changes"`, `publishing.result` kind `no-changes`):** A completed maintenance or investigation run with no diff (`landed: null`). It unblocks `after` dependents once `done`, but does **not** satisfy `watch wait --condition landed` or `delivered`.
  - **Unfinished local push (`publishing.result` kind `local-unpushed`):** The local destination branch advanced, but pushing it to GitHub failed or was refused (`landed: false`). Petrina raises a `stuck` Inbox item whose decision is `inbox retry` (`inbox recovery` is refused). While the task remains open it holds `after` dependents. If you cancel the task (`task cancel`), the task finishes as `cancelled` (`landing: "cancelled"`) while the product result stays `local-unpushed`: on a single-product task that cancellation releases `after` dependents, whereas on a shared task `after` dependents remain held while the unpushed local commit (`localUpdate.pushed: false`) persists.
  - **Interrupted delivery (`publishing.result` kind `interrupted`):** Shipping stopped and Petrina cannot confirm whether the change went out (`landed: false`, `decision: "needed"`). Petrina raises a `shipping` Inbox item; resolve it with `inbox recovery --decision check|ship-again|mark-done`.
  - **Closed without merge (`landing: "closed"`, `publishing.result` kind `pull-request-closed`) or marked done (`landing: "marked-done"`, `publishing.result` kind `unconfirmed`):** Neither is `landed`, and neither satisfies `watch wait --condition landed` or `delivered`. On a single-product task, a closed pull request (`decision: "none"`) or `mark-done` (`unconfirmed`, even if a later GitHub lookup finds a pull request) finishes the task as `done` and releases `after` dependents while recording on them that the prerequisite did not land. On a shared task, an unaccepted closed pull request (`decision: "needed"`) sets `shared: "decision"` and blocks dependents; resolving it with `mark-done` sets `decision: "accepted"` (not `unconfirmed`) and allows the task to finish as `landed` if all other products are delivered and no companion pull request remains open.
  - **Partial shared delivery (`shared` on multi-product tasks):** `publishing.result` and `task.finished` report each product's result alongside `shared`: `unfinished` (any product is still `pending`, `publishing`, `interrupted`, or `local-unpushed`, or companion links are unfinished), `decision` (a product's pull request was closed without merging and still needs your call), `waiting` (all products are delivered or accepted closed, and at least one pull request is still `open`), and `landed` (every product is delivered or accepted closed, and no pull request remains open).
  - **Cancelled (`landing: "cancelled"`, task state `cancelled`):** Work was stopped, which never satisfies `watch wait --condition landed` or `delivered`. `task.finished` lists what each product had already published. Cancellation releases `after` dependents on a single-product task, and on a shared task unless any product still has an open pull request, an unaccepted closed pull request, publishing in progress, or an unpushed local commit.

## Operating loop and handoff

### Compact operating loop

1. **Orient:** Inspect `engine status`, `product list`, `inbox list` and `task list`. Take a starting cursor before acting (`watch events --timeout-ms 0 --json`).
2. **Triage and shape Backlog:** Investigate uncertain reports read-only; check `task list` and `task history` for duplicates; create or update scoped Backlog requests (`task add --backlog`, `task update-backlog`); group overlapping Backlog cards only when product, source and delivery match and without losing scope or provenance; set true `after` prerequisites (`task dependencies`) and `task source` before work starts.
3. **Prioritize and queue:** Admit reviewed Backlog tasks explicitly with `task queue` and order the queue (`task reorder`, `task hold`, `task unhold`).
4. **Resolve Inbox items:** Inspect each item (`inbox inspect`, `learning inspect`, `review-guide inspect`), read all continuation pages, verify `kind`, `revision` and `decisions`, and act within delegated authority using saved `requestId`s. Escalate material product choices or ungranted permissions to the human.
5. **Follow events and verify outcomes:** Wait on `watch events` from the saved `cursor` with a timeout safely below your host's tool deadline. Read focused evidence (`journey check`, `journey finding`, `journey result`, `task health`, `task activity`) only when a transition or blocker warrants it. Verify check passes, review outcomes and per-product landing states before reporting completion.

### Handoff and reporting

When returning control to the human or ending a coordination turn, report concisely in plain language:

- **Queued and decided:** Tasks created, updated, grouped, queued, reordered or held, and Inbox checkpoints, questions, permissions or offers resolved.
- **Landed and published:** Work confirmed `landed`, pull requests `awaiting-merge` (with links for the human to review or merge), and per-product status on shared tasks.
- **Blockers and human decisions:** Open questions, ungranted permission or screen requests, or unresolved check/review/shipping calls that need the human's decision, with your recommended option first.
- **Task and evidence links:** Relevant `taskId`s, `itemId`s, `nodeId`s, check or finding references, and pull-request or release URLs.
- **Saved monitoring cursor:** The latest `watch events` `cursor` and scope so the next turn or session can resume monitoring without missing events or re-reading full tasks.

Do not promise unattended background monitoring or automatic follow-up unless your host environment actively loops and delivers new events into a fresh agent turn. A `watch events` or `watch wait` call only remains open during an active tool call up to its deadline; once your turn finishes, Petrina cannot wake an idle coding agent on its own.
